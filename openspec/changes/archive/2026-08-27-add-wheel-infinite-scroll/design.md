## Context

`BaseWheel` (`sdds-core/uikit-compose/.../internal/wheel/BaseWheel.kt`) реализует одно колесо поверх `SubcomposeLayout` + `LazyColumn`/`LazyListState` (`rememberLazyListState`, `rememberSnapFlingBehavior`). Компонент принимает полностью материализованный `items: List<WheelItemData>`, дополняет его пустыми "Empty"-айтемами по краям через `rememberExtendedList` (для `DataEdgePlacement.WheelCenter`, чтобы первый/последний реальный айтем можно было докрутить до центра), и рендерит получившийся `extendedList` в `LazyColumn` через `items(count = extendedList.size) { index -> ... }`.

Ширина колеса, если не задана извне, вычисляется через `WheelTextMetrics.widestItem` — единственный проход по **всему** `extendedList` с построением intrinsic-text-метрик (`ParagraphIntrinsics`) для каждой уникальной строки, чтобы найти самый широкий элемент. Сам код это уже отмечает как самую дорогую часть измерения (см. комментарий в `BaseWheel.kt` рядом с `widestItem`). Найденный элемент однократно измеряется реальной субкомпозицией внутри `SubcomposeLayout`, и по нему считается итоговая ширина `LazyColumn` и высота ячеек.

Публичного `WheelState`/`rememberWheelState` нет — состояние прокрутки (`LazyListState`) создаётся и хранится внутри `BaseWheel`; наружу утекают только колбэки (`onItemSelected`, `onLabelPositionCalculated`, `onItemHeightCalculated`). Выбор текущего элемента определяется реактивно: `LaunchedEffect(state.firstVisibleItemIndex) { onItemSelected(dataIndex) }`, где `dataIndex` получается вычитанием отступа паддинга (`middleIndex`) из `firstVisibleItemIndex`. Управляющие стрелки (`hasControls`) двигают `state` через `animateScrollToItem`, ограничивая целевой индекс `[0, extendedList.size - 1]` (`maxFirstVisibleItemIndex`).

Готовое зацикливание уже существует в соседней, независимой View-реализации того же компонента (`sdds-core/uikit`, `WheelListView` + `Wheel`), где `Adapter.getItemCount()` возвращает `realItemCount × 20`, а данные достаются по `position % realItemCount`; при остановке скролла рядом с краем этого диапазона происходит невидимый телепорт обратно к середине (`applyInfiniteScroll`). Важно: там расчёт ширины (`estimateMaxChildWidth`) уже читает `adapter.currentList` — реальный, неразмноженный список, отдельно от `getItemCount()` — то есть развязка "данные для измерения" vs "индексное пространство прокрутки" там тоже присутствует, хоть и реализована по-другому. Этот механизм (конечный множитель + recenter-телепорт) сознательно не переносится buквально — для `LazyColumn` в Compose есть более простой и идиоматичный паттерн (см. Decisions).

## Goals / Non-Goals

**Goals:**
- Дать возможность зациклить прокрутку отдельного колеса (`WheelDataSet.looping`), не трогая колёса, для которых зацикливание не нужно, в рамках одного `Wheel(wheelCount = N)`.
- Сохранить текущую стоимость расчёта ширины колеса (`WheelTextMetrics`) неизменной — она должна оставаться пропорциональной размеру реального `items`, а не индексному пространству прокрутки.
- Не ломать существующее поведение non-looping колёс (`looping = false` по умолчанию — аддитивное изменение).

**Non-Goals:**
- Не переносится recenter/teleport-механизм View-реализации (конечный множитель × N, `applyInfiniteScroll` на scroll-idle) — вместо него используется идиоматичный для `LazyColumn` подход с большим виртуальным индексным пространством (см. Decisions).
- Не вводится публичный `WheelState`/`rememberWheelState` — эта задача не расширяет объём управления состоянием снаружи `BaseWheel`, только добавляет `looping`.
- Не рассматривается зацикливание для действительно неограниченных/подгружаемых наборов данных (paging) — `items` остаётся полностью материализованным `List<WheelItemData>`, как и сейчас; "бесконечность" здесь — это зацикленный wrap-around по конечному небольшому списку (часы, дни недели и т.п.), а не открытый диапазон данных.
- Не добавляется валидация/ограничение на `items.size < visibleItemsCount` — одновременная видимость дублирующихся айтемов в разных местах вьюпорта допустима.

## Decisions

### 1. `looping` — поле `WheelDataSet`, не параметр `Wheel(...)`

`WheelDataSet` уже несёт per-колёсные значения (`initialIndex`, `staticTextAfter`, `description`), приходящие через `onSetData(wheelIndex): WheelDataSet`. `dataEdgePlacement`, напротив, сейчас единый параметр `Wheel(...)`, применяемый одинаково ко всем колонкам. Зацикливание должно управляться на уровне отдельного колеса (например, зациклить часы/минуты, но не AM/PM или год) — значит, оно органично ложится в `WheelDataSet`, а не в `Wheel(...)`.

```kotlin
data class WheelDataSet(
    val dataSet: List<WheelItemData>,
    val description: String? = null,
    val initialIndex: Int = 0,
    val staticTextAfter: String? = null,
    val looping: Boolean = false,
)
```

Альтернатива — параметр `Wheel(loopingWheels: Set<Int> = emptySet())` — отклонена: разрывает конфигурацию колеса на два места (`onSetData` и отдельный параметр `Wheel`), тогда как весь остальной per-колёсный конфиг уже стянут в `WheelDataSet`.

Сознательное расхождение с View-реализацией: там `infiniteScrollEnabled` — глобальный параметр `Wheel`, распространяется на все колонки разом. В Compose-версии это несовместимо с целью (зациклить только часть колёс), поэтому паритет с View по форме API не сохраняется — только по смыслу термина "зацикливание".

Нейминг: `looping` (не `infiniteScrollEnabled`, как в View) — выбран сознательно ради краткости, несмотря на терминологическое расхождение между двумя реализациями одного компонента.

### 2. Индексация прокрутки: большое виртуальное пространство + `mod`, без recenter

Для `looping = true` колесо строится не поверх `extendedList` (с dummy-паддингом краёв), а поверх независимого виртуального индексного пространства:

```kotlin
LazyColumn(state = state, ...) {
    items(count = Int.MAX_VALUE) { virtualIndex ->
        val item = items[virtualIndex.mod(items.size)]
        // ...рендер, transform-логика — как сейчас
    }
}
```

Начальная позиция `LazyListState` анкерится не в 0, а рядом с серединой диапазона, выровненной по `items.size`, чтобы пользователь мог прокручивать в обе стороны, не упираясь в границы `Int` при разумной длительности использования экрана:

```kotlin
val anchor = (Int.MAX_VALUE / 2).let { it - it.mod(items.size) }
rememberLazyListState(initialFirstVisibleItemIndex = anchor + initialIndex)
```

Recenter/teleport-логика (как `applyInfiniteScroll` в View-версии) не нужна: расстояние от анкера до реального края `Int.MAX_VALUE` (~1 млрд позиций в каждую сторону) недостижимо при любом реалистичном использовании колеса в рамках одной композиции. Это стандартный, широко используемый в Compose-сообществе приём для зацикленных `LazyColumn`/`LazyRow`/`Pager` — он проще, чем конечный множитель с телепортом, и не требует отслеживания `scrollState == Idle`.

Альтернатива — конечный множитель (по образцу View, `items.size × N` с recenter на scroll-idle) — рассмотрена и отклонена: добавляет отдельный класс багов (видимый прыжок при неточном recenter, необходимость синхронизировать recenter с анимациями/fling) ради экономии, которая в Compose не нужна — `LazyColumn` уже виртуализирует рендер вне зависимости от заявленного `count`.

### 3. Развязка `WheelTextMetrics` от индексного пространства прокрутки — ядро решения исходной проблемы

`WheelTextMetrics` (построение `widestItem`, `maxItemTextWidth` и т.д.) продолжает вызываться **только** с реальным `items: List<WheelItemData>`, независимо от `looping`. Ни `Int.MAX_VALUE`, ни виртуальный индекс, ни `virtualIndex.mod(items.size)` никогда не передаются в код измерения ширины — он не знает о зацикливании вообще. Именно это разделение источника данных для измерения (всегда конечный, реальный список) и индексного пространства прокрутки (потенциально огромное только для looping-колёс) снимает исходную проблему: наивное "размножить список" ломало бы измерение, потому что раньше `extendedList` одновременно обслуживал и рендер, и метрики.

### 4. `DataEdgePlacement` не применяется к looping-колесу

`rememberExtendedList`/dummy-паддинг (`WheelCenter`) существует, чтобы первый/последний реальный элемент мог оказаться в центре вьюпорта у конечного списка. У зацикленного колеса нет "первого/последнего" элемента с точки зрения UX — оно бесшовно продолжается в обе стороны, поэтому паддинг для него не нужен и не применяется: при `looping = true` `dataEdgePlacement`, переданный в `Wheel(...)`, игнорируется для этого конкретного колеса (без ошибки/предупреждения — переданное значение просто не участвует в построении looping-ветки).

### 5. Выбор элемента и управляющие стрелки — по модулю, без клампа

`onItemSelected` для looping-колеса вычисляет реальный индекс данных как `centerVirtualIndex.mod(items.size)` (аналогично текущему вычитанию `middleIndex`, но без клампа по границам — зацикленность получается автоматически через `mod`, а не через явную wrap-логику).

Управляющие стрелки (`hasControls`, текущие `controlTargetIndex`/`controlScrollJob`) для looping-колеса просто инкрементируют/декрементируют **виртуальный** индекс (`state.animateScrollToItem(virtualIndex ± 1)`) без клампа по `[0, size - 1]`, в отличие от текущей логики для non-looping колёс, которая ограничивает целевой индекс `extendedList.size`.

## Risks / Trade-offs

- **[Риск]** Виртуальный индекс — обычный `Int`; при экстремально долгой сессии скролла (существенно больше, чем реалистичный юзкейс) теоретически возможно приближение к границе `Int.MAX_VALUE`.
  → **Митигация**: не митигируется намеренно (см. Non-Goals/Decision 2) — общепринятый в Compose-практике трейдофф для этого паттерна; достижение границы требует скролла на ~1 млрд позиций в рамках одной композиции, что не является реалистичным сценарием использования UI-виджета.
- **[Риск]** Два разных механизма зацикливания в одном компоненте `Wheel` для двух платформ (View: конечный × N + recenter; Compose: `Int.MAX_VALUE` + mod, без recenter) усложняют ментальную модель для разработчиков, работающих с обеими реализациями.
  → **Митигация**: явно документируется в KDoc `WheelDataSet.looping` и в этом design-документе, что механизмы не идентичны намеренно; наименование поля (`looping` vs `infiniteScrollEnabled`) тоже сигнализирует о том, что это независимые API.
- **[Риск]** `looping = true` вместе с `dataEdgePlacement`, явно заданным вызывающей стороной, молча игнорирует `dataEdgePlacement` для этого колеса — может быть неожиданно для потребителя API.
  → **Митигация**: зафиксировать поведение в KDoc `WheelDataSet.looping` ("при `looping = true` значение `dataEdgePlacement`, переданное в `Wheel`, для этого колеса не применяется").
- **[Trade-off]** `items.size < visibleItemsCount` при `looping = true` может показать один и тот же айтем дважды одновременно во вьюпорте — визуально это может выглядеть непривычно для очень коротких списков (2-3 элемента).
  → Осознанно принято как допустимое поведение (см. proposal), без валидации/ограничения.

## Migration Plan

Изменение аддитивное — `WheelDataSet.looping` по умолчанию `false`, поведение существующих вызовов не меняется. Отдельного миграционного плана или отката не требуется; фиче-флага не нужно — включение per-колёсное и явное через API.
