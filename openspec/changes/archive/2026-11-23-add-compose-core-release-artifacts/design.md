## Context

База подготовки: `origin/develop`, `0b6cc75ad`. В этом репозитории ветка разработки называется `develop`.

`integration-core/preview-compose-plugin` уже извлекает `sdds/api/uikit-compose-api-meta.json` из JVM-артефакта UIKit, использует его для генерации фабрик и кладёт исходный файл в ZIP как `api-meta.json`. `generatePreviewManifest` записывает `commit`, `version = commit.take(12)`, `uikitComposeVersion` из трёх чисел в `gradle.properties` и SHA-256 меты. Существуют проверки состава ZIP и production preview в браузере. CI публикует сборки `develop` и релизных источников через DS Builder CLI.

DS Builder change `version-core-entities-and-preview` требует неизменяемые координаты `(libraryId, platform, version)` и отдельный явный канал `stable/dev`. Любая ДС хранит выбранные канал и конкретную версию отдельно для каждой платформы; импорт пополняет список доступных версий и обновляет явно подписанные latest-черновики. Изменённые байты или нормализованный состав под теми же координатами отклоняются. На `develop` версия `uikit-compose` меняется реже исходников: добавления только `coreRelease` в шаблон недостаточно.

## Goals / Non-Goals

**Goals:** выпускать совместимые Compose-архивы с явным выбором канала при публикации, отделить Core от preview build ID, воспроизводимо получить A/B/B2 и передать измеримые результаты в DS Builder.

**Non-Goals:** менять генерацию кода ДС, алгоритм KSP, Kotlin API основной библиотеки, формат массива меты, Preview Protocol v1, системные состояния или серверную логику публикации. Сборка артефактов не требует публикации Maven-пакетов. Проверочное удаление не должно попасть в обычную поставку UIKit.

## Decisions

### 1. Координаты добавляются в manifest, исходная мета сохраняется

| Поле | Источник и смысл |
|---|---|
| `channel` (запрос загрузки, вне ZIP) | Явный `--channel stable|dev`; неизменяемый атрибут зарегистрированного Core |
| `coreRelease.libraryId` | Постоянное `uikit-compose`, согласованное с примерами импорта DS Builder |
| `coreRelease.platform` | Постоянное `compose`, совпадает с платформой manifest |
| `coreRelease.version` | Явная версия поставляемого Core-снимка по правилам ниже |
| `uikitComposeVersion` | То же значение, что `coreRelease.version` |
| `commit` | Полный SHA исходников preview |
| верхнеуровневое `version` | Первые 12 hex SHA-256 от commit, libraryId, platform и Core version, разделённых переводом строки |
| `apiMetaSha256` | SHA-256 точных байтов `api-meta.json` из архива |

Идентификатор библиотеки не настраивается отдельно для A/B: сервер разрешает одну библиотеку на платформу. В локальном контуре с ранее импортированным другим `libraryId` нужен отдельный каталог/БД, а не автоматическое переименование библиотеки.

Канал передаётся вызывающим CLI при загрузке рядом с `coreRelease`, не входит в ZIP или исходную мету и не расширяет ключ уникальности координат. Он неизменяем у зарегистрированного релиза: тот же version нельзя повторно выдать в другом канале. Стабильная поставка проверенного dev-состава регистрируется отдельным стабильным релизом с собственной версией. Ни dev, ни stable импорт не переключает уже настроенные ДС с pinned; выбор выполняется только в настройках самой ДС.

Существующая цепочка `previewApiMeta → extractPreviewApiMeta → generatePreviewManifest → previewPluginArtifact` остаётся. В ней один источник меты для JVM/Wasm-зависимости, фабрик, хеша и ZIP. `components` manifest по-прежнему описывает рендеримые истории; это не фильтр состава Core-меты. Не добавляем JSON-оболочку или повторную сериализацию меты.

Проверка распакованного ZIP расширяется на все координаты, их согласованность и строгий формат SHA-256. Негативные тесты намеренно повреждают копии артефакта; они не используются как успешные A/B.

### 2. Явная политика версий без изменения общих Gradle conventions

Упаковка принимает необязательный `coreVersion` как Gradle input и записывает эффективную версию одновременно в `uikitComposeVersion` и `coreRelease.version`. Канал не входит в сборку: CLI требует `--channel stable|dev` при загрузке, независимо от ZIP, ref и URL dev/prom.

- Dev CI передаёт channel=dev и `<baseVersion>-dev.<fullSourceCommit>`, где baseVersion берётся из `uikit-compose/gradle.properties`, а SHA — из реально выбранного checkout. Два коммита с изменившейся метой не претендуют на одну стабильную версию. Локальная упаковка без параметра версии применяет это же правило без выбора канала.
- Для стабильной поставки CI передаёт channel=stable и `baseVersion` только после проверки источника релиза UIKit и соответствия версии. Произвольная ветка не объявляется стабильным Core только потому, что выбрано окружение `prom`; при недоказанном источнике отправка останавливается.
- A использует channel=stable и версию подтверждённого UIKit-релиза. B использует channel=dev и `<baseVersion>-ab.b.<commitB>`. Исходники Core A берутся из подтверждённого стабильного релиза; новый producer допускается собрать отдельно, сохранив доказательство соответствия Core этому релизу. B строится из того же Core с проверочным patch, не из произвольного следующего develop. Проверочные артефакты поставляются только в изолированный контур.
- Для нового preview того же Core допускается явный повтор версии, если точные байты меты совпадают с исходной поставкой. B2 использует канал и версию B и другой preview-коммит. Сервер остаётся окончательной проверкой неизменяемости; конфликт не обходится автоматической сменой версии и повторной отправкой.

Это версии Core-снимков, объявляемые производителем; Maven-координаты и версия локальной зависимости не переписываются. Для stable/A значение совпадает с версией UIKit, а для dev, включая B/B2, содержит явно документированный prerelease-суффикс. Клиент не выводит координаты из меты или её хеша.

Сборка и CLI не проверяют чистоту Git-дерева и не требуют фиксации локальных изменений. `previewCommit` указывает на настоящий базовый HEAD, но не доказывает точное содержимое рабочего дерева; фактический состав проверяется по мете и байтам архива. Смена `coreVersion` автоматически формирует новый build ID при том же HEAD. Канал загрузки не меняет ZIP или ID; смена канала уже зарегистрированного Core отклоняется. Изменённый ZIP того же Core заменяет незакреплённый dev-preview, остальные случаи отклоняются. Повторная отправка использует сохранённый ZIP; воспроизводимость пересборки проверяется отдельно.

Альтернатива «версия только из gradle.properties» отвергнута из-за конфликтов на develop. Изменение общерепозиторного Maven-versioning избыточно: задача касается поставки каталога/preview.

### 3. Проверочные исходники A/B изолированы от продукта

Рецепт и исходные patch-файлы находятся рядом с модулем preview, например в `src/coreReleaseTest/`. Достаточно небольшого сценария подготовки и существующих Gradle-задач; отдельный release framework и новый included build не нужны.

Рецепт получает зафиксированный producer commit с реализацией этого change и подтверждённый стабильный Core ref для A и создаёт отдельные временные checkout. Для A/B/B2 сохраняются настоящие локальные fixture-коммиты и переносимое свидетельство их исходников (Git bundle либо экспорт исходников с patch-файлами и проверяемым tree SHA). Они не пушатся в продуктовые ветки; исходный checkout не изменяется. A/B получают отдельные build directories, чтобы исключить смешение результатов KSP/Wasm.

Конкретный сценарий на текущем Core:

- **A (stable):** исходная мета содержит `TextField.cursorColorReadOnly` и `TextArea.cursorColorReadOnly` с `deprecated.message = "Use cursorColor"`.
- **B (dev):** в изолированной копии `TextFieldStyleBuilder.kt` удаляется только `@ApiDeprecated("Use cursorColor")` у соответствующей перегрузки. Обе перегрузки уже имеют `@Deprecated`; текущий KSP исключает их из меты без `@ApiDeprecated`. Методы остаются в Kotlin API. В B также добавляется проверочный компонент `CoreChannelProbe` с API-метой и рендеримой историей, переиспользующий существующий стиль/рендерер; он существует только в изолированных исходниках B/B2. Мета заново получается обычным KSP, фабрики и настоящий Wasm пересобираются из B.
- **B2:** исходники Core и мета B неизменны; отдельный preview-коммит меняет только проверочную подпись плагина. Версия Core явно остаётся B, build ID отличается. B2 нужен для проверки, что поздно закреплённый preview не заменяется следующей сборкой того же Core.

Проверка рецепта требует наличия всех ожидаемых перегрузок/аннотаций и останавливается при изменившейся базе. Сравнение A/B подтверждает отсутствие выбранного свойства у обоих компонентов, наличие нового CoreChannelProbe только в B, неизменность остальных записей и наличие совместимого `cursorColor`. Ручное редактирование `api-meta.json`, копирование Wasm из A в B и подмена manifest готового ZIP не допускаются. Структурное сравнение разрешено только для диагностики, не для записи файла меты.

Deprecated-свойство уже пропускается preview-генератором. Поэтому проверка A не требует визуального эффекта от него: проверяется сохранённая конфигурация/экспорт, warning и успешная отрисовка компонента. Для переноса выбирается свободное назначение `cursorColor` в точно той же области; отдельный сценарий выполняет удаление. Это техническая проверка переноса, а не автоматическая миграция семантики readonly.

### 4. Комплект передачи и граница ответственности

В локальном каталоге результатов, исключённом из Git, сохраняются для A/B/B2:

- `preview-compose-plugin.zip`, извлечённая из него без изменения `api-meta.json` и manifest;
- receipt с `libraryId/platform/channel/coreVersion`, source commit/tree, build ID, SHA-256 меты и всего ZIP, базовым producer commit и checksum patch/исходников;
- команды с параметрами, версии JDK/Gradle/Node/Chrome, результаты JVM/проверки архива/browser test, ссылка на исходники, отчёт diff меты A/B;
- инструкция настройки двух обычных ДС на stable/A с выбранными компонентом/оформлением/назначением и свободным целевым свойством; идентификаторы конкретной БД получаются при импорте, не зашиваются в переносимый fixture.

Секреты и сессии не попадают в receipt. Рецепт собирает артефакты без сети к DS Builder и не публикует их автоматически. Внешний прогон использует отдельный локальный контур с совместимыми backend/CLI из DS Builder change; реальные HTTP-коды, IDs, counts и хеши фиксируются в отдельном отчёте, а не заранее объявляются успешными.

Сценарий передачи:

1. Проверить dry-run stable/A, опубликовать preview A через CLI и настроить две обычные ДС на Compose stable/A; у первой сохранить активный TextField с `cursorColorReadOnly` и явно опубликовать версию с непустым журналом. Зафиксировать также выбор другой платформы, например web stable, и модель/экспорт/preview ID.
2. Импортировать **только мету B** с координатами B и channel=dev. Обе ДС сохраняют A, прежние отчёты/экспорт/preview, draftRevision/coreSelectionRevision и журнал; CoreChannelProbe отсутствует в их доступном каталоге. В настройках первой ДС явно выбрать Compose dev/B: только её Compose меняется, появляется CoreChannelProbe и конфликт сохранённого свойства. Вторая ДС, другая платформа и история A неизменны. Preview B ещё отсутствует, редактор доступен; новый fetch/export и прямая публикация конфликтного черновика отклоняются.
3. Пройти сводку → «Проблемы»; проверить удаление и перенос, сохранение/откат и конфликт параллельной правки и выбора Core по coreSelectionRevision. Для двух действий использовать независимые seed-состояния. После исправления и с непустым журналом явно опубликовать ДС B **до** публикации preview B.
4. Опубликовать ZIP B: ожидающий слот опубликованной ДС B заполняется один раз. Опубликовать B2: историческая ДС B сохраняет первый build ID, а A сохраняет A. Запустить поддерживаемую сервером очистку с посторонней незакреплённой сборкой и проверить доступность закреплённых URL/байтов. Повторная отправка A не меняет явно выбранный dev/B. Следующий черновик наследует канал/версию публикации. Регистрация последующего stable-релиза только добавляет его в список; переход любой ДС требует явного сохранения выбора.
5. Проверить локальную генерацию из сохранённого снимка A при недоступном сервере и локальном Core B. Запуск генератора не требует совпадения Core; сборка/тесты полученного кода отдельно показывают реальную совместимость.

Полный набор вариаций/сочетаний/состояний и негативных исправлений берётся из задач 8.2–8.4 DS Builder. Android предоставляет реальные артефакты; серверные assertions и UI-прогон выполняются в его контуре. Один evidence-отчёт можно использовать для обоих change, без дублирования серверного тестового инструментария в Android.

### 5. CI, документация и проверка

Расширяется существующий workflow: явные канал и версия Core, прежние тесты/сборка, проверка архива, совместимый закреплённый CLI, dry-run и разрешённая отправка. Версия CLI выбирается по реально опубликованному релизу с `coreRelease`, номер не выдумывается. Пока такого релиза нет, локальный прогон использует CLI из DS Builder worktree; автоматическая отправка остаётся выключенной. A/B-рецепт не вызывает prom workflow.

README обновляет таблицу полей, параметры, политику dev/release, происхождение меты и инструкцию A/B. README поясняет настройки platform/channel/version любой ДС: новый импорт продвигает только latest выбранного канала, а повторная отправка не переключает сохранённый выбор ни вперёд, ни назад. Dev/stable не являются признаками ДС; например Compose dev/B и web stable/A могут использоваться одновременно. Новые публичные Gradle-типы, если понадобятся, документируются KDoc; общий DSL `dsBuilder` и его генераторы не расширяются ради этой задачи.

Основные команды запускаются из корня репозитория, для каждого проверочного checkout и с его `-PcoreVersion`; канал указывается позднее в команде загрузки:

```bash
./gradlew -p integration-core :preview-compose-plugin:jvmTest
./gradlew -p integration-core :preview-compose-plugin:previewPluginArtifact :preview-compose-plugin:verifyPreviewPluginArtifact -PcoreVersion=<version>
./gradlew -p integration-core :preview-compose-plugin:previewPluginBrowserTest -PcoreVersion=<version> -PpreviewChromePath=<chrome>
```

В примерах показан dev; для A передаётся stable с подтверждённой стабильной версией.

Негативные тесты validator/version selection добавляются в тот же модуль с документированной командой запуска. Линтеры запускаются по затронутым модулям. Если потребуется изменить KSP или общие conventions, это выходит за выбранное узкое решение и требует пересмотра design.

## Risks / Trade-offs

- [Dev-версия отличается от Maven-версии] → явно документировать смысл `uikitComposeVersion` как версии поставляемого Core; сохранять baseVersion и source SHA в receipt, не менять Maven dependency resolution.
- [Изменения меты без нового commit] → новая явная Core-версия формирует отдельный детерминированный build ID; прежние Core-координаты остаются неизменяемыми.
- [Изменилась форма TextField API] → проверять предусловия patch и точный diff меты; не выбирать другое свойство молча.
- [Невоспроизводимый ZIP или потерянные локальные fixture-коммиты] → хранить оригинальные ZIP, хеши, переносимые исходники и проверять повторную сборку. Без источников проверка не считается воспроизводимой.
- [Старый CLI/backend либо отсутствующий browser/S3] → prerequisite отмечается отсутствующим, внешний этап не считается пройденным.

## Migration Plan

1. Реализовать и проверить producer локально; согласовать пример `uikit-compose/compose/version` с DS Builder.
2. Получить A/B/B2 и пройти связанный локальный контур. Не отправлять проверочные prerelease в общие dev/prom каталоги.
3. Перед включением CI развернуть совместимый backend и закрепить выпущенный CLI. Пересобрать архивы из исходников; старые ZIP не исправлять на месте.
4. При проблемах выключить автоматическую отправку. Уже сохранённые Core/preview не удаляются и не перезаписываются; исправление выпускается под новыми координатами/ID. Возврат старого producer без нового manifest несовместим с новым сервером.

## Open Questions

- Какой опубликованный релиз DS Builder CLI станет первым совместимым? Это условие включения CI; локальная сборка CLI позволяет выполнить A/B до его выпуска.
- Конкретные стабильный Core ref A, SHA producer/A/B/B2 и контрольные суммы появятся при реализации. Они не заменяются фиктивными значениями в этом proposal.

### Режим последней версии в DS Builder

Настройка каждой платформы ДС допускает конкретную версию (pinned) или latest выбранного stable/dev. latest разрешается сервером DS Builder по последнему зарегистрированному Core (created_at DESC, id ASC), без анализа semver; интерфейс показывает «Последняя (номер версии)» внутри списка, без отдельной подписи. Producer по-прежнему передаёт только конкретные неизменяемые координаты; канал задаётся при загрузке, без latest в manifest, Gradle-версии или исходной мете. Новый импорт обновляет только подписанные latest-черновики; pinned и опубликованные границы сохраняются. Повторная отправка и preview B2 не продвигают Core. Следующий черновик наследует политику latest, а локальные снимки остаются конкретными и автономными. Изменение producer-кода для latest не требуется.

### Повторная загрузка локального dev-preview

Producer сохраняет детерминированный build ID при прежних базовом коммите и Core-версии. Изменённый preview с прежним Core допускает замену через dsbuilder preview-plugin publish --apply. Сервер разрешает её только для dev и без исторического закрепления, сохраняя неизменяемость Core-координат и меты. Stable, новая мета либо исторический слот требуют отдельной версии/сборки. Без --apply выполняется только проверка; dryRun ничего не пишет. Служебные каталоги S3 переключаются атомарно и очищаются после замены; публичный URL меняется, build ID остаётся прежним. Gradle сам ничего не загружает; Обычная загрузка, в том числе из CI, применяет те же серверные ограничения.
