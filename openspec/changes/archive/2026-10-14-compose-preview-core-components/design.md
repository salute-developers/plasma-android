## Context

Preview Protocol уже умеет передавать всё, что нужно Core-компонентам (шаг 2). Плагин же знает один компонент:
`BasicButton` зарегистрирован вручную в `Main.kt`, фабрика стиля написана вручную, список `components` в manifest — строка.

Факты, на которые опирается change (проверены по коду на ветке `feature/compose-preview-payload-v2`):

- В `uikit-compose-fixtures` было 74 истории `@Story`; 69 из них имели запись в `uikit-compose-api-meta.json` (79 компонентов меты) по имени `ComponentKey`.
  `BottomSheetStory` тоже относится к мете: она строит `ModalBottomSheetStyle`, то есть это компонент `ModalBottomSheet` (ключ называется иначе). Без компонента меты остаются четыре истории:
  `Icon`, `Text` (стиль `NoStyle`), `IconTabs` (тот же `TabsStyle`, что у `Tabs`, отдельного компонента меты нет) и `Mask` (стиль `TextFieldStyle`, компонента `Mask` в мете нет).
  Девять компонентов меты историй не имели (`AccordionItem`, `DropdownEmptyState`, `DropdownLoadingState`, `IconTabItem`, `ListItem`,
  `NavigationDrawerItem`, `SelectItem`, `TabBarItem`, `TabItem`). В DS Builder такие компоненты настраиваются отдельно: свойство-стиль родителя хранит ссылку
  на оформление дочернего компонента (`<styleName>[.<axis>...]`, таблицы `component_style_references` и `appearances`), у которого свои вариации и свойства.
  Показывает ли интерфейс редактора их как самостоятельные карточки, не проверено (D9b).
  Ключи `ComponentKey` для них уже были; публичный composable есть у всех, кроме `DropdownEmptyState` и `DropdownLoadingState`, но и они отрисовываются
  (`DropdownScope.EmptyState` вызывается в пустом `DropdownScope`, `FooterLoadingState` самостоятельный).
- Мета описывает для каждого компонента `componentName`, `qualifiedName` класса билдера, `styleQualifiedName` и список параметров
  с перегрузками (`id`, `methodName`, `paramQualifiedType`, `valueQualifiedType`, `group`, `type`). Виды параметров:
  color, dimension, typography, shape, component_style, value, float, icon, shadow, boolean, integer. `stateEnum` есть у 20 компонентов.
- `builderFunName` (имя функции стиля, создающей билдер) задан только у 5 из 79 записей (`Badge`, `BasicButton`, `IconBadge`, `IconButton`, `LinkButton`),
  потому что у `BadgeStyle` и `ButtonStyle` несколько билдеров. У остальных 74 вход в билдер это `<Style>.builder()` из companion стиля: проверено текстовым поиском
  `fun builder(...): <Builder>` в исходниках `uikit-compose` для всех 74 записей; корректность по companion и сигнатуре подтверждается компиляцией.
- Среди 69 компонентов с историями: простые (A) 17; только кастомные состояния (B) 10; только вложенные стили (C) 17;
  B и C вместе 6; иконки или тени (D) без остального 3; C и D вместе 13; B, C и D вместе 3.
- `StoryRegistry` хранит истории по `ComponentKey`, но не умеет их перечислять; `registerStories()` генерирует `sandbox-ksp`.
- В Kotlin/Wasm нет рефлексии: вызовы билдеров по имени метода должны быть сгенерированы заранее.

Публикация: `preview-contract`, `preview-sdk-compose`, `sandbox-core`, `sandbox-ksp`, `sandbox-compose` и `uikit-compose-fixtures` применяют `convention.maven-publish`;
`preview-compose-plugin` нет (это архив для браузера). Релизные workflow в `.github/workflows` есть только для `sandbox-*`.

## Goals / Non-Goals

**Goals:**
- Один механизм вместо ручной фабрики на компонент: генерация по мете.
- Совпадение выбора перегрузок билдера с Theme Builder (иначе preview разойдётся с тем, что получает приложение).
- Покрыть фазы A, B, C для 69 компонентов с историями и фазу E: истории для дочерних компонентов.
- Список компонентов manifest и реестр плагина берутся из одного источника.

**Non-Goals:**
- Фаза D: иконки (`ImageSource`) и тени (`ShadowAppearance`). Нужны painter'ы для SVG/PNG и маппинг теней (вне шага 2).
- Изменение Theme Builder и общий модуль логики стилей с ним (отложено в плане, см. «Отложенное»).
- Preview выпущенных версий, доставка плагина в S3, проверка Edge/Firefox.
- Расширение редактора клиента (прозрачность, градиенты, вложенные стили в UI).

## Decisions

### D0. Форма генератора выбирается спайком: KSP (A) или Gradle-задача (B)

Два варианта, оба выдают одни и те же фабрики:

- **A. KSP-процессор** в новом модуле `preview-ksp`. Видит настоящие классы UIKit: может проверить перегрузки и найти точку входа в билдер, узнать значения enum'ов.
- **B. Gradle-задача** с KotlinPoet, читающая JSON и пишущая исходники в `build/generated/`. Проще в отладке и не зависит от KSP, но не видит классы: точку входа берёт из меты
  и соглашения `Style.builder()`, enum'ы разбирает через `valueOf(...)`, ошибки типов находит только компиляция сгенерированного кода.

Спайк выбирает B, если для 79 записей хватает меты и соглашения (первая задача спайка: проверка точек входа и типов), и A, если часть компонентов нельзя обработать без анализа классов.
Остальные решения (D1–D9) не зависят от выбора.

**Результат спайка: выбран B** (Gradle-задача и KotlinPoet, модуль `integration-core:preview-generator`, не публикуется). Мета и соглашения хватило для всех 79 записей, см. «Результаты спайка».

### D1. Фабрики порождаются для всех компонентов меты, а не для историй

Генератор (в любом из вариантов D0) не видит истории (они лежат в другом модуле), но ему они и не нужны: фабрика зависит только от записи меты.
Это же даёт фабрики для компонентов без историй, которые нужны как вложенные стили (`ListItem`, `TabItem` и др.).
Связь «история и фабрика» устанавливается во время запуска по `componentId`. Альтернатива (генерировать фабрики там, где лежат истории) отвергнута:
вложенные стили без историй остались бы без фабрик.

### D2. Реестр историй строится в sandbox-ksp и перечисляется через `StoryRegistry`

`sandbox-ksp` уже генерирует `registerStories()` и знает класс истории; он дополняется записью `{componentId, story, styleQualifiedName}`.
`styleQualifiedName` берётся из аргументов типа `ComposeBaseStory<State, Style>`. `componentId` задаётся в `@Story` явно и равен имени компонента в мете.
Он НЕ равен `ComponentKey.value`: значение ключа строится из имени константы (`CHECKBOX` → `Checkbox`), и у шести историй оно отличается от меты
(`CheckBox`, `CheckBoxGroup`, `CircularProgressBar`, `ProgressBar`, `RadioBox`, `RadioBoxGroup`). Поэтому сверка идёт с метой (тест покрытия), а не с ключом.
SDK принимает `componentId` отдельным параметром (`previewComponentOf(componentId, story, factory)`), а не берёт `story.component.value`.

### D2a. Совместимость публичного API

`sandbox-core`/`sandbox-ksp` публикуются и могут использоваться внешними историями, поэтому `@Story(componentId)` необязателен (пустая строка): история без идентификатора
работает в `StoryRegistry` как раньше и просто не участвует в preview. Забытый идентификатор у нашей истории ловит тест покрытия (история без фабрики должна быть в списке исключений).
Генератор фабрик не публикуется и не становится зависимостью публичных модулей.

### D2b. Истории для дочерних компонентов (фаза E)

Дочерние компоненты настраиваются в DS Builder самостоятельно, поэтому preview должен уметь показать и их, а не только внутри родителя (замечание ревью).
**Результат (задача 2a):** написаны девять историй (состояние `@StoryUiState`, `@Story(componentId)`, `Content` и `Preview`): `AccordionItem`, `IconTabItem`, `ListItem`,
`NavigationDrawerItem`, `SelectItem`, `TabBarItem`, `TabItem`, `DropdownEmptyState`, `DropdownLoadingState`. Айтемы рисуются самостоятельно без родителя (`Local*` стили имеют значения по умолчанию);
`DropdownEmptyState` вызывает `DropdownScope.EmptyState` в пустом `object : DropdownScope`. `BottomSheetStory` получила `componentId = "ModalBottomSheet"`.
Итог: у каждого из 79 компонентов меты ровно одна история с идентификатором; исключены из preview только четыре истории без компонента меты (`Icon`, `Text`, `IconTabs`, `Mask`).
Побочный эффект: новые истории регистрируются в `StoryRegistry` как остальные; демо-приложение показывает компоненты по провайдеру стилей темы, поэтому новые истории появятся там, когда тема их стилизует.
Публичный API `uikit-compose-fixtures` только расширяется.

### D3. Сборка компонента из type-erased записей

`previewComponent(story, factory)` типизирован дженериками. Для реестра добавляется функция, принимающая `ComposeBaseStory<*, *>` и
`ComposePreviewStyleFactory<*>` и проверяющая совпадение классов стиля до непроверяемого приведения. Несовпадение — ошибка запуска плагина
(это ошибка сборки, а не пользовательского payload).

### D4. Правила выбора перегрузки и оформления значения живут в генераторе

Правила записаны в спеке и реализованы в генераторе фабрик заново. Theme Builder не меняется. Страховка от расхождения — дифференциальный тест на конфигах golden-тестов
Theme Builder (`UniversalComposeVariationGeneratorTest`, `GenerateComponentsTaskTest`). Без него preview может разойтись с кодом, который Theme Builder
генерирует для приложения. Альтернатива (общий модуль) отложена; рекомендация плана при возврате: начать с вынесения только выбора перегрузки.

### D5. Предупреждения собираются до построения стиля по метаданным фабрики

Фабрика создаётся в Composable-контексте, и вернуть из неё предупреждения неудобно. Поэтому каждая сгенерированная фабрика экспортирует данные для предупреждений
(`states`, `unsupportedProperties`, `gradientUnsupportedProperties`, `nestedStyleTypes`, `styleQualifiedName`), а SDK собирает предупреждения и проверяет вложенные стили в `prepare()`
(`collectWarnings`, `validateNestedStyles`), не вызывая Composable. Свойства вложенного стиля проверяются по правилам компонента, которому принадлежит стиль
(реестр `GeneratedPreviewStyleFactories`), а не по правилам корневого. Данные и построение стиля порождаются из одной меты, поэтому не расходятся.

### D6. Имена кастомных состояний

Имя кастомного состояния сопоставляется с `configName` константы `stateEnum` (по умолчанию имя константы) без учёта регистра: так делает Theme Builder
(`PropertyMapper.customStateValues` сравнивает `configName.lowercase()`), поэтому `checked` и `Checked` равнозначны. Интерактивные состояния (`pressed`, `hovered`, ...) сравниваются точно.
Клиент может отправлять любой регистр. Реализовано в `PreviewStateMap` (SDK), проверено в браузере для CheckBox (`Indeterminate`).

### D7. Вложенные стили: тип проверяется по мете

Для параметра `component_style` фабрика берёт стиль из `payload.styles`, определяет фабрику по `style.component` и сравнивает тип результата с типом параметра.
Циклы и неизвестные ссылки уже отсекает `validateReferences` (шаг 2), поэтому рекурсия конечна.

### D8. Иконки и тени пропускаются

Пока SDK не умеет создавать painter из SVG/PNG, свойства `icon` и `shadow` получают значение по умолчанию и предупреждение `unsupported_property`.
Компонент с иконкой при этом рисуется, но без пользовательской иконки.

### D9a. Живая проверка: галерея и выборочное сравнение

Автотесты (покрытие, дифференциальный тест) не доказывают, что компонент рисуется. Поэтому браузерный тест `previewPluginBrowserTest` получает два уровня:

- Галерея: все компоненты реестра, payload из меты с пробными значениями, проверка успеха, допустимых предупреждений и непустого холста, скриншоты в одну HTML-страницу.
  Скриншоты снимаются через тот же DevTools-протокол Chrome, что использует существующий тест; пробные значения подбираются по виду свойства (цвет, размер, форма, типографика, состояния, вложенный стиль).
- Выборочное сравнение с эталоном: один компонент на фазу (A, B, C). Эталон — та же история со стилем, собранным в тесте прямым вызовом билдера UIKit.
  Сравнение проверяет, что фабрика применяет значения так же, как прямой код; соответствие настоящей теме приложения проверяет дифференциальный тест с Theme Builder.

Галерея не доказывает правильность цветов и размеров, она ловит падения и грубые визуальные ошибки; точность проверяется выборочным сравнением.

### D9b. Что умеет клиент для остальных компонентов

Клиент собирает payload из соответствий свойств Compose (`composeParameters`) и метаданных (`Meta.preview.compose`).
**Результат проверки (спайк, 1.4):** привязка к Compose есть только у `Button` и зашита в клиенте (`LEGACY_COMPOSE_PREVIEW_BINDINGS` в `js/apps/client/src/utils/api.ts`: `Button` → `BasicButton`).
`Meta.preview.compose` из бэкенда (`db-service`) для других компонентов не приходит: я не нашёл места, где оно заполняется. Модель БД поддерживает платформу `compose`
(`component_platform`, `property_platform`), и импорт api-меты платформо-зависим, но заполненность соответствий `compose` у других компонентов не проверялась.
Следствие: пока клиент не получит привязку компонент→`componentId` и соответствия свойств, Compose-режим в настоящем редакторе заработает только для кнопки, независимо от плагина.
Остальные компоненты проверяются галереей (4.6) и сравнением с эталоном (4.7). Привязка и соответствия оформляются отдельным change в design-system-builder.

### D9. Спайк до остальной работы

Первым этапом на 5 компонентах: BasicButton (перегрузки `StatefulValue`), CheckBox (кастомные состояния), TextField (значения и перечисления), Avatar (`Brush` и `StatefulValue`),
Tabs (вложенные стили). Спайк подтверждает правила выбора перегрузки и оформление значений и сразу получает дифференциальный тест на этих пяти. Результаты фиксируются в этом `design.md`
до массовой генерации.

## Risks / Trade-offs

- **Расхождение с Theme Builder** → дифференциальный тест (D4); риск остаётся для конфигов вне golden-тестов.
- **Размер Wasm-артефакта** (79 фабрик, 74 истории) → замер размера и времени холодного старта до и после; прежние значения: 4,23 МБ, 279–322 мс на localhost.
- **Время компиляции** KSP и Kotlin/Wasm растёт → замер; при необходимости генерировать фабрики только для компонентов с историями и их вложенных стилей.
- **Версия меты расходится с версией UIKit в клиентской дизайн-системе** (дизайн-система могла быть сгенерирована старой версией Theme Builder) → мета берётся из той же версии `uikit-compose`, что и плагин; несовпадение свойств даёт предупреждение, а не ошибку.
- **Клиент не умеет собирать payload для остальных компонентов** (см. D9b) → проверка в спайке; до тех пор компоненты проверяются галереей, а не в настоящем редакторе.
- **Хрупкая приёмка состояний кастомных enum'ов** → тест на каждое значение `stateEnum` по всей мете.

## Migration Plan

1. Спайк на 5 компонентах, правка правил в этом документе.
2. Реестр и manifest, генератор фабрик (форма по результату спайка, D0), SDK-обобщение.
3. Удаление `BasicButtonPreviewStyleFactory` после того, как сгенерированная фабрика `BasicButton` проходит прежние браузерные проверки.
4. Откат: вернуть ручную фабрику и запись в `Main.kt` (одна ветка, данные не мигрируют).

Документация: KDoc публичного API (`@Story`, `StoryRegistry`, сборка компонента), раздел в README плагина о том, как добавить компонент в preview (теперь это аннотация, а не код).
Команды валидации: `./gradlew :integration-core:sandbox-ksp:test (и тесты генератора: `:integration-core:preview-ksp:test`, если выбран KSP) :integration-core:preview-sdk-compose:jvmTest :integration-core:preview-compose-plugin:jvmTest :integration-core:preview-compose-plugin:previewPluginBrowserTest`, затем `./gradlew testAll detektAll spotlessApplyAll`.

## Open Questions

Решены разработчиком:

- Фаза D (иконки и тени) не входит в этот change; отдельный change после появления painter'ов для SVG/PNG (D8).
- Истории без компонента меты (`Icon`, `Text`, `IconTabs`, `Mask`; `BottomSheet` относится к `ModalBottomSheet`) исключаются из preview и вносятся в список исключений теста покрытия.
- Порога размера артефакта нет: размер и холодный старт измеряются на спайке и после полной генерации (задачи 1.x и 5.2); при заметном росте решение возвращается разработчику с цифрами.

Решены разработчиком (после ревью): истории для дочерних компонентов добавляются сразу в этом change (D2b).

Закрыто спайком:

- Написание кастомных состояний: сопоставление без учёта регистра (D6). Клиент сейчас отправляет только `hovered` и `pressed` (`PropState`).
- Что умеет клиент для остальных компонентов (D9b).

Остаётся (спайк не затрагивал):

- Нужен ли стабильный `key` у `@StoryProperty` или достаточно имени поля `UiState` (решить при работе над реестром, задача 2).

## Результаты спайка

Спайк выполнен на ветке `feature/compose-preview-core-components` (2026-10-13) для BasicButton, CheckBox, TextField, Avatar, Tabs; генерация и компиляция проверены на всей мете.

- **Точки входа.** У 5 записей есть `builderFunName`, у остальных 74 в исходниках UIKit есть `fun builder(...)` с нужным типом билдера (проверено текстовым поиском).
  Сгенерированный код для всех 79 записей компилируется под Wasm (`compileKotlinWasmJs`) после правки двух расхождений меты ниже.
- **Мета достаточна для варианта B.** Для свойств `value` мета содержит список значений enum (`values` с `configName`, по умолчанию равным имени); все такие типы это enum или `Boolean`/`Int`.
  Анализ классов не потребовался.
- **Особенности меты.** (1) Свойство `dimensions` у `AvatarGroup` имеет вид `dimension`, но принимает `AvatarGroupDimensions`: перегрузки с несоответствующим типом значения пропускаются.
  (2) Устаревшие свойства (`deprecated`) пропускаются, как в Theme Builder. (3) Пара `(группа, id)` задаёт место вызова; вложенные группы (`dimensions.indicatorDimensions`) отдаются вложенными блоками.
- **Дифференциальный тест** (`ThemeBuilderDifferentialTest`, модуль `preview-generator`) использует классы Theme Builder через включённую сборку `sdds-core` и `-Xfriend-paths`, а не копию правил.
  Сравнивает выбор перегрузки для 945 не-цветовых свойств и 330 цветовых (для сплошного цвета и градиента) по всей мете: расхождений нет; изменение приоритета в генераторе роняет тест с именем свойства (проверено).
  Тест требует JVM 17 (Theme Builder собран под 17, а конвенции репозитория задают 11), поэтому у модуля `preview-generator` цель 17.
- **Браузерная проверка** (`previewPluginBrowserTest`, headless Chrome): BasicButton (прежние проверки, теперь сгенерированной фабрикой), CheckBox (кастомные и составные состояния, `Indeterminate`
  в другом регистре без предупреждений, неизвестное состояние даёт `unknown_state`), TextField (enum-значения, неизвестное значение игнорируется), Avatar (вложенный Badge), Tabs (вложенные TabItem и Divider): все успешны.
- **Размер** (фабрики всех 79 компонентов в Wasm): архив 4,23 → 5,01 МБ (+0,78 МБ, +18%); Wasm приложения 3,55 → 6,93 МБ сырых (0,93 → 1,70 МБ в gzip); Wasm Skiko не изменился. Порога нет.
  Время холодного старта на этом этапе не замерялось (задача 5.2).
- **Известные упрощения спайка.** Тип вложенного стиля, не совпавший с параметром, молча пропускается (`style_type_mismatch` будет в задаче 4.2); у цвета без перегрузки с `Brush` градиент игнорируется без предупреждения;
  из многослойного градиента берётся первый слой; порядок записей `InteractiveColor` разворачивается так же, как у `StatefulValue` (отдельно не проверялся).
- **Попутно.** Для регистрации историй в плагине нужен вызов `registerStories()` до создания runtime (раньше он стоял в `main()`).

## Результаты реализации (задачи 2–5)

- **Реестр и истории.** `StoryRegistry.previewEntries()` отдаёт 79 записей, по одной на компонент меты. 69 историй получили `componentId` по имени из меты, `BottomSheetStory` стала
  `ModalBottomSheet` (её стиль `ModalBottomSheetStyle`), добавлено девять историй айтемов (D2b). Без preview остались четыре истории без компонента меты (`Icon`, `Text`, `IconTabs`, `Mask`).
  Дубликат `componentId` роняет сборку KSP с именами обеих историй (проверено на реальных историях).
- **Генерация.** Все 79 фабрик строятся генератором; метаданные фабрики (`states`, `unsupportedProperties`, `gradientUnsupportedProperties`, `nestedStyleTypes`, `styleQualifiedName`) используются для предупреждений и проверки
  вложенных стилей (`style_type_mismatch`, `style_component_not_found`) до отрисовки; предупреждения вложенных стилей проверяются по правилам их компонента-владельца.
- **Manifest.** `components` генерируется из списка фабрик (шаблон `src/manifest/preview-plugin.template.json`); ручная фабрика `BasicButtonPreviewStyleFactory` удалена.
  Браузерный тест проверяет, что все компоненты manifest описываются плагином, а компонента вне manifest нет.
- **Галерея** (4.6) отрисовывает все 79 компонентов в production-артефакте: успех, пустой список предупреждений, непустой кадр, ошибки страницы, застывший рендер, скриншоты и HTML-страница.
  Галерея нашла дефект артефакта, который не ловили другие проверки: Compose-ресурсы историй (`composeResources`, 1,5 МБ) не входили в архив, и первая же история с ресурсом (`Avatar`) останавливала рендер всех следующих;
  ресурсы добавлены в архив. Первая версия проверки «в кадре больше одного цвета» оказалась пустой (на всех снимках был индикатор загрузки), поэтому добавлены сбор ошибок страницы и проверка застывшего рендера;
  для headless Chrome нужен программный WebGL (`--use-angle=swiftshader`), иначе холст Compose не попадает в скриншот.
- **Сравнение с эталоном** (4.7) выполнено на уровне стилей, а не скриншотов: JVM-тест строит стиль фабрикой и вручную прямым вызовом билдера для BasicButton (A), CheckBox (B) и Tabs (C) и сравнивает поведение
  (`getValue` по наборам состояний, значения). Скриншотное сравнение потребовало бы отдельного Wasm-приложения с эталонными стилями в артефакте; сравнение стилей точнее (видит состояния, а не только кадр по умолчанию)
  и не зависит от рендеринга. Проверено мутациями: игнорирование прозрачности и потеря порядка записей роняют тест.
- **Размер и холодный старт** (5.2): архив 4,23 → 5,74 МБ (+1,51 МБ, +36%; из них 1,5 МБ несжатых Compose-ресурсов); Wasm приложения 3,55 → 6,93 МБ сырых (0,93 → 1,70 МБ gzip).
  Холодный старт (5 запусков Chrome, смоук клиента): медиана 290 мс, минимум 285, максимум 309 мс; значения шага 1 были 279–322 мс, то есть без заметных изменений. Порога нет (решение разработчика).

- **Попапы и уведомления.** Истории `Modal`, `ModalBottomSheet`, `Popover`, `Tooltip`, `Toast`, `Notification` рисуют только кнопку-триггер; галерея кликает по центру и проверяет, что кадр
  изменился и в нём не меньше трёх цветов (снимки `<id>-open.png`). Для `Toast` и `Notification` плагин теперь оборачивает содержимое в `OverlayHost` (как песочница) с отдельным менеджером оверлеев на каждый payload,
  иначе уведомления не показывались и оставались на экране при следующих render; в галерее для них выключено автоскрытие. Одинаковые кадры у разных компонентов допускаются только из явного списка
  (общий стиль или общая кнопка-триггер), ожидание кадра идёт до стабилизации, а не фиксированной паузой.
- **Правки по независимому ревью.** Сгенерированные фабрики без лишних `if/else` с одинаковыми ветками; запись состояния без имён отклоняется (`invalid_state_entry`); `previewComponentsFrom` не принимает
  запись с неопределённым классом стиля; добавлены тесты градиента, literal-цвета и `InteractiveColor` на настоящих фабриках (мутации ловятся); дифференциальный тест сверяет выбор по тем же фильтрам, что и генерация;
  JVM 17 в `preview-generator` поднят только для тестов, фабрики запускаются на JVM 17 через `javaLauncher`; `integration-core/kotlin-js-store/` добавлен в `.gitignore`.
  Осознанно не сделано: нераспознанный цвет в градиентном токене по-прежнему молча пропускает значение (без предупреждения); дубликат `componentId` между разными модулями KSP не проверяется.

### Риск: исключение при композиции останавливает рендер

`success` отправляется после применения состояния, до отрисовки, а исключение внутри `Content()` (например, `MissingResourceException`) не возвращается результатом и останавливает рендер до перезагрузки страницы.
Compose не позволяет `try/catch` вокруг вызовов composable, поэтому в плагине это не обернуть. Сейчас такие случаи ловит галерея (ошибки страницы, застывший рендер); для пользователя нужен отдельный механизм
(например, проверка кадра хостом или изолированный рендер); вынесено за рамки этого change.
