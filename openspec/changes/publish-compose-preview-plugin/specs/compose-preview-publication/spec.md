## ADDED Requirements

### Requirement: Плагин публикуется отправкой архива на бэкенд DSB

Публикация SHALL отправлять собранный `preview-compose-plugin.zip` на бэкенд Design System Builder командой CLI `dsbuilder preview-plugin publish`. Репозиторий `plasma-android` MUST NOT записывать файлы плагина в S3 напрямую и MUST NOT хранить ключи записи в хранилище.

#### Scenario: Архив отправляется командой CLI

- **WHEN** workflow публикации доходит до шага отправки
- **THEN** он MUST вызвать `dsbuilder preview-plugin publish --platform compose --from preview-compose-plugin.zip` с адресом API окружения
- **AND** workflow MUST NOT содержать шагов записи в S3.

#### Scenario: Секреты хранилища отсутствуют

- **WHEN** проверяются workflows и Gradle-конфигурация публикации
- **THEN** они MUST NOT ссылаться на ключи, endpoint или бакет S3.

### Requirement: Окружение определяется триггером

Workflow SHALL отправлять билд на dev-бэкенд при изменении `develop` в затрагивающих плагин путях и на prom-бэкенд на каждом релизном теге независимо от списка изменённых модулей. `workflow_dispatch` MUST позволять запустить публикацию для выбранного окружения. Публикации в одно окружение MUST выполняться последовательно, без отмены выполняющейся публикации.

#### Scenario: Push в develop публикует на dev

- **WHEN** в `develop` попадает коммит, изменяющий файлы плагина, его зависимостей или `build-system`
- **THEN** workflow MUST отправить билд этого коммита на dev-бэкенд.

#### Scenario: Релиз публикует на prom

- **WHEN** `publish-release` обрабатывает релизный тег
- **THEN** workflow публикации плагина MUST быть запущен для этого тега
- **AND** билд MUST быть отправлен на prom-бэкенд, даже если модуль плагина отсутствует в списке изменённых модулей релиза.

#### Scenario: Публикации в одно окружение не перекрываются

- **WHEN** две публикации в одно окружение запускаются одновременно
- **THEN** вторая MUST ожидать завершения первой.

### Requirement: Отправка проходит гейты качества и пробную отправку

Перед отправкой workflow SHALL выполнить `:preview-compose-plugin:jvmTest` и `previewPluginBrowserTest` на собираемом артефакте, а на релизном теге проверку `check-preview-contract` в режиме `error`. Затем workflow SHALL выполнить пробную отправку без `--apply` и только после её успеха отправку с `--apply`.

#### Scenario: Провал теста блокирует отправку

- **WHEN** `jvmTest`, `previewPluginBrowserTest` или проверка контракта завершается ошибкой
- **THEN** CLI MUST NOT вызываться и бэкенд MUST остаться без изменений.

#### Scenario: Провал пробной отправки блокирует запись

- **WHEN** пробная отправка завершается ошибкой
- **THEN** отправка с `--apply` MUST NOT выполняться.

#### Scenario: Расхождение контракта блокирует релизную публикацию

- **WHEN** на релизном теге копия Preview Protocol не совпадает с каноническим контрактом design-system-builder
- **THEN** публикация на prom MUST быть остановлена.

### Requirement: Доступ к бэкенду выдаётся служебной учёткой окружения

Workflow SHALL получать адрес API и учётные данные служебной учётки из секретов репозитория отдельно для каждого окружения. Учётные данные MUST передаваться CLI через переменные окружения процесса, MUST NOT попадать в аргументы команды и MUST NOT выводиться в лог.

#### Scenario: Секрет не попадает в лог

- **WHEN** workflow выполняет шаги публикации
- **THEN** значение секрета служебной учётки MUST NOT присутствовать ни в аргументах команд, ни в выводе шагов.

#### Scenario: Окружения не смешиваются

- **WHEN** билд отправляется на dev-бэкенд
- **THEN** workflow MUST использовать адрес и учётные данные dev, а не prom.

### Requirement: Повторная публикация безопасна

Повторный запуск workflow для того же коммита SHALL завершаться успехом, если бэкенд сообщает, что билд уже опубликован без изменений. Если бэкенд сообщает конфликт (тот же билд, другое содержимое архива), workflow MUST завершиться ошибкой с сообщением бэкенда.

#### Scenario: Тот же коммит публикуется повторно

- **WHEN** workflow перезапускается для коммита, уже опубликованного на окружении
- **THEN** workflow MUST завершиться успехом
- **AND** сообщение шага MUST сообщать, что билд уже опубликован.

#### Scenario: Конфликт содержимого

- **WHEN** бэкенд отвечает конфликтом для билда того же коммита
- **THEN** workflow MUST завершиться ошибкой и показать причину.

### Requirement: Документация описывает публикацию

README плагина SHALL описывать состав артефакта, поля manifest, схему публикации (триггеры, окружения, роль CLI и бэкенда) и локальную проверку: сборку zip, запуск локального контура DSB и отправку командой CLI.

#### Scenario: Разработчик проверяет публикацию локально

- **WHEN** разработчик читает раздел публикации в README плагина
- **THEN** README MUST содержать команды сборки артефакта и отправки на локальный бэкенд
- **AND** README MUST указывать, что запись в хранилище выполняет бэкенд DSB, а не `plasma-android`.
