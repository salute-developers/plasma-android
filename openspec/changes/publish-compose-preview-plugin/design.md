## Context

`:integration-core:preview-compose-plugin` собирает self-contained Kotlin/Wasm-плагин `preview-compose-plugin.zip` (`index.html`, `preview-plugin.json`, `*.js`, `*.wasm`, `composeResources/`; ~12 МБ распакованным, ~4 МБ в zip). Публикации нет. Web-клиент DSB загружает плагин по адресу из конфигурации, читает `preview-plugin.json`, проверяет `protocolVersion` и открывает плагин в `iframe`.

Факты о репозитории, на которых стоит дизайн:

- Плагин зависит от `libs.sdds.uikit.compose`, но `convention.core-dependencies` (применён в `integration-core`) подменяет `io.github.salute-developers:sdds-uikit-compose` локальным проектом `sdds-core:uikit-compose`. Плагин и его `api-meta.json` всегда собираются из локальных исходников коммита, а не из опубликованного артефакта.
- Версия `uikit-compose` лежит в `sdds-core/uikit-compose/gradle.properties` (`versionMajor/Minor/Patch`); `libs.versions.toml` содержит версию последнего опубликованного релиза и на `develop` может отставать от исходников.
- Модуль плагина перечислен в `.ignore-changed-modules`, поэтому `changed-modules.sh` его не видит и релизные workflows не запускают публикацию по изменению модуля.
- `publish-release` рассылает `repository_dispatch` по изменённым модулям; для плагина нужен безусловный запуск.
- Бэкенд DSB (change `host-compose-preview-plugin`) принимает архив плагина, кладёт файлы в S3, импортирует мету из `api-meta.json` и хранит версии в БД. Один экземпляр бэкенда обслуживает одно окружение (dev или prom).

## Goals / Non-Goals

**Goals:**
- Автоматическая публикация плагина на dev-бэкенд DSB по `develop` и на prom-бэкенд по релизному тегу.
- В `plasma-android` нет ключей записи в S3 и знания о хранилище.
- Билд несёт идентификацию, по которой бэкенд сверяет архив и мету: версия `uikit-compose`, sha256 меты, коммит.
- Публикация безопасна при повторном запуске и не заменяет билд при провале проверок.

**Non-Goals:**
- Хранение, индекс версий, очистка, выбор билда клиентом, импорт меты: всё это на стороне DSB.
- Trust policy плагина: проверка origin, подпись артефакта.
- Публикация с feature-веток: проверка выполняется локальным zip.
- Выдача и настройка служебной учётки (Keycloak, gateway): change в design-system-builder.

## Decisions

### 1. Идентификация билда в manifest и артефакте

Шаблон `preview-plugin.template.json` дополняется полями, которые подставляет `generatePreviewManifest`:

| Поле | Значение |
|---|---|
| `commit` | полный sha коммита сборки |
| `version` | первые 12 символов `commit` (идентификатор билда) |
| `uikitComposeVersion` | версия из `sdds-core/uikit-compose/gradle.properties` |
| `apiMetaSha256` | sha256 файла `api-meta.json` из артефакта |

`api-meta.json` копируется в артефакт из того же ресурса, из которого `generateComposePreview` строит фабрики (`previewApiMeta` → `sdds/api/uikit-compose-api-meta.json`). Версия — человекочитаемая метка, sha256 — точная привязка к мете: на `develop` исходники могут опережать версию в `gradle.properties`. Бэкенд сверяет sha256 файла в архиве с `apiMetaSha256` manifest.

### 2. Публикация — вызов CLI, а не загрузка в S3

CI не знает о хранилище: он вызывает `dsbuilder preview-plugin publish --platform compose --from preview-compose-plugin.zip --api-url <окружение>` (команда и контракт — в change `host-compose-preview-plugin`). CLI читает `api-meta.json` из архива, нормализует мету (как `components import-api`), проверяет согласованность с manifest и отправляет архив и нормализованную мету на бэкенд одним запросом; бэкенд сам кладёт файлы в S3, импортирует мету и записывает билд.

Альтернатива — публикация в S3 из Gradle (`S3UploadTask`, индекс версий, каналы, чистка). Отклонена: у репозитория не должно быть ключей хранилища DSB, а согласование версии плагина с метой и очистка требуют данных бэкенда.

### 3. Окружения и триггеры

| Окружение | Триггер | Источник | Бэкенд |
|---|---|---|---|
| dev | push в `develop` с фильтром путей (`integration-core/preview-*`, `integration-core/sandbox-core`, `integration-core/uikit-compose-fixtures`, `sdds-core/uikit-compose`, `build-system`, `gradle/libs.versions.toml`) и `workflow_dispatch` | исходники ветки | dev-бэкенд DSB |
| prom | `publish-release` запускает workflow безусловно с тегом релиза; `workflow_dispatch` с тегом | исходники тега | prom-бэкенд DSB |

Публикация привязана к релизному тегу, а не к публикации `uikit-compose`: плагин зависит ещё от фикстур, SDK, контракта и sandbox-core, а workflow `uikit-compose` запускается только при изменении самого модуля.

Адрес API, идентификатор и секрет служебной учётки задаются секретами репозитория отдельно для каждого окружения (`DSB_API_URL_<ENV>`, `DSB_CLIENT_ID_<ENV>`, `DSB_CLIENT_SECRET_<ENV>`). Workflow использует `concurrency` с группой на окружение и `cancel-in-progress: false`, чтобы публикации в одно окружение не перекрывались.

### 4. Гейты и пробная отправка

Порядок шагов: сборка артефакта, `:preview-compose-plugin:jvmTest`, `previewPluginBrowserTest`, на релизном теге `check-preview-contract` в режиме `error`, затем **пробная отправка** (`dsbuilder preview-plugin publish` без `--apply`: бэкенд валидирует архив и мету и ничего не пишет) и только после неё отправка с `--apply`. Падение любого шага до отправки оставляет бэкенд без изменений. Пробная отправка ловит ошибки формата и авторизации до записи.

### 5. Идемпотентность и повтор

Билд идентифицируется коммитом. Повторный запуск workflow для того же коммита отправляет тот же архив: бэкенд отвечает «без изменений». Если архив того же коммита отличается по содержимому (недетерминированная сборка Wasm), бэкенд отвечает конфликтом, и workflow падает с понятным сообщением. Для релизного тега такой конфликт требует разбора: повторная сборка не должна молча подменять уже опубликованный билд.

### 6. Установка CLI в CI

CLI `dsbuilder` собирается под JVM и macOS; сегодня он поставляется только как macOS-архив. Для CI предлагается JVM-дистрибутив (архив со стартовыми скриптами, Java 17), который публикует репозиторий DSB вложением GitHub Release (тег `cli-vX.Y.Z`, задачи в change `host-compose-preview-plugin`). Workflow `plasma-android` скачивает закреплённую версию (версия в workflow, обновляется осознанно) и запускает CLI на `ubuntu-latest` с уже установленным JDK 17. Если репозиторий DSB закрыт, для скачивания релиза нужен токен чтения (секрет).

### 6a. Браузерный тест на ubuntu

`previewPluginBrowserTest` по умолчанию ищет Chrome по пути macOS; в CI путь задаётся свойством `-PpreviewChromePath` (на `ubuntu-latest` Chrome установлен в системе, путь определяется `which google-chrome`). Node приходит через Gradle-плагин Kotlin, как и при локальной сборке Wasm.

### 7. Секреты и права

Учётка в DSB имеет роль «публикация Compose preview»: она может вызывать только маршрут публикации и не имеет прав системного администратора. Секрет не выводится в логи; CLI получает его из переменных окружения процесса, а не из аргументов команды.

## Проверка

| Что проверяется | Как |
|---|---|
| Поля manifest и соответствие sha256 файлу `api-meta.json` | расширение существующих тестов артефакта (`jvmTest`, `previewPluginBrowserTest`) |
| Состав артефакта: `api-meta.json`, manifest, wasm | проверка списка файлов zip в тесте задачи артефакта |
| Workflow: фильтр путей, вызов из `publish-release`, `concurrency`, гейт «тест упал, значит отправки нет» | пробный прогон `workflow_dispatch` на ветке с пробной отправкой (без `--apply`) против dev-бэкенда; один прогон с намеренно упавшим тестом подтверждает гейт |
| Сквозная проверка | локальный контур DSB (`./setup-local.sh`): zip из `plasma-android` отправляется командой CLI, клиент показывает плагин из MinIO контура |
| Бэкенд, CLI, авторизация | тесты в change `host-compose-preview-plugin` |

## Risks / Trade-offs

- [CLI недоступен на раннере: у него цели JVM и macOS] → JVM-дистрибутив в CI или macOS-раннер; закрепление версии.
- [Секрет служебной учётки в репозитории] → роль только на публикацию, секрет по окружениям, не в аргументах, ротация через DSB.
- [Недетерминированный архив одного коммита приводит к конфликту при повторе] → бэкенд сообщает конфликт явно; кеш артефакта шага сборки между пробной отправкой и отправкой.
- [Новый workflow на каждый push в `develop`: сборка Wasm и браузерный тест требуют Chrome и Node] → фильтр путей; время сборки измеряется на первой реализации.
- [Отправка на prom до готовности бэкенда] → публикация на prom включается после выкладки бэкенда с маршрутом; до этого шаг для prom отключён флагом.
- [Расхождение версии CLI и бэкенда] → команда CLI проверяет совместимость по ответу бэкенда; несовместимость завершает шаг ошибкой.

## Migration Plan

1. Добавить поля manifest и `api-meta.json` в артефакт (обратно совместимо: клиент игнорирует неизвестные поля).
2. Дождаться бэкенда с маршрутом публикации и служебной учётки в dev.
3. Включить workflow для dev, проверить пробной отправкой, затем с `--apply`.
4. Включить публикацию на prom вместе с вызовом из `publish-release`.

Откат: отключить workflow или шаг отправки; бэкенд хранит прежний активный билд.

## Open Questions

- Доступ CI к GitHub Release репозитория DSB с JVM-дистрибутивом CLI, если репозиторий закрыт (формат поставки подтверждён).
- Реальные имена секретов и адреса dev- и prom-бэкендов, которые зададут владельцы инфраструктуры.
- Время сборки плагина в CI: измерить на первом запуске.

Решённые вопросы: фильтр путей для `develop` сохраняется (список в разделе «Окружения и триггеры»); имена секретов по соглашению `DSB_API_URL_<ENV>`, `DSB_CLIENT_ID_<ENV>`, `DSB_CLIENT_SECRET_<ENV>`; Chrome на ubuntu-раннере есть, путь передаётся свойством.
