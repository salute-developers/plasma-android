## Context

`:integration-core:preview-compose-plugin` собирает self-contained Kotlin/Wasm-плагин `preview-compose-plugin.zip` (`index.html`, `preview-plugin.json`, `*.js`, `*.wasm`, `composeResources/`; ~12 МБ распакованным). Публикации нет. Web-клиент DSB загружает плагин по `VITE_COMPOSE_PREVIEW_PLUGIN_URL`, читает `preview-plugin.json`, проверяет `protocolVersion`, требует, чтобы entrypoint был того же origin, и открывает его в `iframe` с `sandbox="allow-scripts allow-same-origin"`.

Факты о репозитории, на которых стоит дизайн:

- Плагин зависит от `libs.sdds.uikit.compose`, но `convention.core-dependencies` (применён в `integration-core`) подменяет `io.github.salute-developers:sdds-uikit-compose` локальным проектом `sdds-core:uikit-compose`. Плагин и его `api-meta.json` всегда собираются из локальных исходников коммита, а не из опубликованного артефакта.
- Версия `uikit-compose` лежит в `sdds-core/uikit-compose/gradle.properties` (`versionMajor/Minor/Patch`); `libs.versions.toml` содержит версию последнего опубликованного релиза и на `develop` может отставать от исходников.
- Модуль плагина перечислен в `.ignore-changed-modules`, поэтому `changed-modules.sh` его не видит и релизные workflows не запускают публикацию по изменению модуля.
- В `build-system/conventions/.../tasks/s3` уже есть `S3BaseTask`/`S3UploadTask` (обёртка над `s3cmd`, `--delete-removed`, `--signature-v2`, `--no-mime-magic`) и функции чтения `S3_*` секретов; docs/dokka публикуются по схеме `<ветка>/<тип>/<artifactId>/<версия>/`.
- Бакет плагина — бакет DSB (в DSB-репозитории секреты `AWS_*`, `AWS_S3_BUCKET_2`). Клиент DSB лежит в этом же бакете по пути `<env>/design-system-builder/client/`.

Потребитель (отдельный change в design-system-builder) выбирает билд по версии `uikit-compose`, закреплённой в БД бэкенда: берёт запись индекса с наибольшей версией, не превышающей закреплённую; если такой нет, берёт последний билд канала; в обоих неточных случаях показывает предупреждение.

## Goals / Non-Goals

**Goals:**
- Автоматическая публикация плагина в S3 на `develop` (канал `dev`) и на релизном теге (канал `current`).
- Неизменяемые билды и атомарное переключение: клиент никогда не видит смесь файлов двух билдов.
- Метаданные, позволяющие клиенту сопоставить билд с api-метой, импортированной в БД DSB: версия `uikit-compose` и sha256 меты.
- Мета, по которой собран плагин, публикуется вместе с билдом и служит единственным источником для импорта.
- Совместимость по протоколу выражена путём (`protocol-<N>`), поэтому плагин с новым протоколом не ломает клиенты со старым.

**Non-Goals:**
- Импорт меты в БД, хранение пина, выбор билда и откат на клиенте (change в design-system-builder).
- Trust policy: allowlist origin, подпись артефакта.
- Публикация с feature-веток: проверка выполняется локальным zip и override `VITE_COMPOSE_PREVIEW_PLUGIN_URL`.
- Автоматический импорт меты (требует роли `system_admin`, у автоматизации такого доступа нет).

## Decisions

### 1. Неизменяемые билды плюс индекс канала (а не один изменяемый путь)

```
compose-preview/
  builds/<build-id>/                      immutable: index.html, preview-plugin.json, api-meta.json, *.js, *.wasm, composeResources/
  protocol-<N>/<channel>/index.json       единственный изменяемый файл канала
```

Публикация: (1) залить `builds/<build-id>/`; (2) прочитать индекс канала, добавить или заменить запись, записать индекс. Индекс пишется последним — это точка переключения.

Альтернатива — перезапись одного пути (`sync --delete-removed`). Отклонена: заливка неатомарна, `.js` не имеет хеша в имени, кеширование в браузере эвристическое, `--delete-removed` удаляет файлы, нужные открытым вкладкам.

`<build-id>` = первые 12 символов sha коммита (например, `746d05193312`): один коммит даёт один билд, поэтому повторный запуск не плодит каталоги. Дата публикации хранится в `publishedAt` индекса.

Если каталог `builds/<build-id>/` уже существует, публикация не перезаливает файлы (билды неизменяемы, а байты Wasm у повторной сборки могут отличаться). Она читает `preview-plugin.json` существующего билда, убеждается, что `commit` совпадает с текущим, и переходит к обновлению индекса. При несовпадении `commit` публикация завершается ошибкой.

### 2. Формат индекса

```json
{
  "schemaVersion": 1,
  "protocolVersion": 1,
  "channel": "current",
  "versions": [
    {"uikitCompose": "0.55.0", "build": "746d05193312", "apiMetaSha256": "…", "publishedAt": "…"}
  ]
}
```

Одна запись на версию `uikit-compose`; повторная публикация той же версии заменяет запись (в канале `dev` — на каждом push в `develop`, в `current` — когда релиз не менял версию, но изменил плагин). Версии отсортированы по убыванию semver. Индекс хранит не более N=10 последних версий. Относительные пути к билдам клиент строит как `<base>/builds/<build>/`; индекс не содержит абсолютных URL, чтобы бакет можно было перенести.

### 3. Каналы и триггеры

| Канал | Триггер | Источник |
|---|---|---|
| `dev` | push в `develop` (с фильтром путей: `integration-core/preview-*`, `integration-core/sandbox-core`, `integration-core/uikit-compose-fixtures`, `sdds-core/uikit-compose`, `build-system`, `gradle/libs.versions.toml`) и `workflow_dispatch` | исходники ветки |
| `current` | `publish-release` запускает workflow безусловно с тегом релиза; `workflow_dispatch` с тегом | исходники тега |

Публикация привязана к релизному тегу, а не к публикации `uikit-compose`: плагин зависит ещё от фикстур, SDK, контракта и sandbox-core, а workflow `uikit-compose` запускается только при изменении самого модуля.

Workflows используют `concurrency` с фиксированной группой на канал и `cancel-in-progress: false`: индекс обновляется как read-modify-write, параллельные публикации в один канал должны выполняться последовательно.

### 4. Идентификация билда в manifest

Шаблон `preview-plugin.template.json` дополняется полями `version` (`<build-id>`), `uikitComposeVersion` (из `sdds-core/uikit-compose/gradle.properties`), `apiMetaSha256`, `commit`. Значения подставляет `generatePreviewManifest`. `api-meta.json` копируется в артефакт из того же ресурса, из которого `generateComposePreview` строит фабрики (`previewApiMeta` → `sdds/api/uikit-compose-api-meta.json`); sha256 считается от этого файла.

Версия — человекочитаемая метка, sha256 — точная привязка к мете: в `dev` исходники могут опережать релизную версию.

### 5. Gradle-задача публикации на `S3UploadTask`

`previewPluginPublish` в модуле плагина: распаковывает артефакт в промежуточный каталог, заливает в `builds/<build-id>/`, обновляет индекс. Параметры подключения — существующие `s3-*`/`S3_*`; канал, префикс и протокол — Gradle properties. Задача выполняется и локально (против тестового префикса), и в CI. Альтернатива — шаг `s3cmd` в workflow (как в DSB) — отклонена: логику порядка и индекса сложнее воспроизвести и проверить локально.

`S3UploadTask` использует `--no-mime-magic` и `--delete-removed`; для публикации билда `--delete-removed` отключается (каталог билда новый), а Content-Type и Cache-Control задаются явно по расширению файла (см. п. 6). Если `S3UploadTask` не позволяет задать заголовки по маске, расширение задачи вносится в `build-system/conventions` с проверкой, что `docusaurusDeploy`/`dokkaDeploy` остаются без изменений.

### 5a. Хранилище как порт

Логика публикации (раскладка ключей, проверка существования билда, слияние индекса, план очистки, порядок «билд, затем индекс») пишется как чистый Kotlin-код над интерфейсом хранилища (`put`, `get`, `exists`, `list`, `delete` с метаданными заголовков). Реализации: `s3cmd`-адаптер поверх `S3BaseTask` для CI и локальная файловая реализация для тестов. Это позволяет проверять атомарность и сбои без бакета. Альтернатива — вызывать `s3cmd` прямо из задачи — отклонена: поведение при сбое между шагами невозможно проверить без реального S3.

### 6. Заголовки объектов

`s3cmd` определяет Content-Type по расширению через Python `mimetypes`; результат зависит от версии. Явно задаём:

| Файл | Content-Type | Cache-Control |
|---|---|---|
| `*.wasm` | `application/wasm` | `public, max-age=31536000, immutable` |
| `*.js` | `text/javascript; charset=utf-8` | `public, max-age=31536000, immutable` |
| `index.html`, `preview-plugin.json`, `api-meta.json` | `text/html` / `application/json` | `public, max-age=31536000, immutable` (путь содержит build-id, файл не меняется) |
| `index.json` канала | `application/json` | `no-cache` |

Правильный Content-Type нужен для `WebAssembly.instantiateStreaming` (браузер отвергает wasm с другим типом). Ограничение по CORS и разрешение iframe (отсутствие `X-Frame-Options`/`frame-ancestors`) — настройки бакета DSB, а не этого change; фиксируются в README как требования к хостингу.

### 7. Хранение

Чистка выполняется самой задачей публикации после успешного обновления индекса:

1. Собрать множество билдов, на которые ссылается любой индекс любого протокола.
2. Удалить каталоги `builds/*`, не входящие в это множество и старше 30 дней.

Lifecycle-правило бакета по возрасту не используется: билд, закреплённый в индексе канала `current` для старой версии `uikit-compose` (откат), может быть старше любого порога. Индекс ограничен N=10 версиями, поэтому объём ограничен 2×N билдов на протокол (~240 МБ несжатыми).

### 8. Размещение в бакете клиента и origin

Плагин размещается в том же бакете, что и клиент DSB (`AWS_S3_BUCKET_2` в репозитории DSB). Origin плагина при этом может совпасть с origin клиента: клиент открывает плагин в `allow-same-origin` iframe, и при общем origin код плагина мог бы читать `localStorage` клиента с access и refresh токенами. Риск принят осознанно: плагин публикует только команда SDDS (см. также Non-Goals: trust policy). Публикация не блокируется отдельным хостом, но базовый URL остаётся параметром, а не вшивается в код, чтобы позже вынести плагин на отдельный хост без изменений формата.

Общий бакет накладывает два практических ограничения:

- **Раздельные префиксы.** Плагин лежит в собственном префиксе (`<prefix>/compose-preview/`), не вложенном в префикс клиента: выкладка клиента выполняет `s3cmd sync --delete-removed` в `.../client/` и удалила бы вложенные файлы плагина. Публикация плагина записывает только в свой префикс и не использует `--delete-removed` на уровне префикса клиента.
- **Ключ записи ограничен префиксом плагина.** Ключ, используемый в этом репозитории, MUST NOT иметь прав на префиксы клиента и админки, чтобы ошибка публикации не могла перезаписать клиент.

Альтернатива (отдельный хост или поддомен для плагина) остаётся желательной и описана как будущее изменение; она не требует изменения формата индекса или manifest.

## Проверка

| Что проверяется | Как |
|---|---|
| Слияние индекса, сортировка, обрезка, план очистки | unit-тесты чистой логики |
| Порядок «билд, затем индекс», сбой между шагами, повторная публикация существующего билда, параллельные публикации | интеграционный тест на локальной файловой реализации хранилища (инъекция сбоя на загрузке файла билда) |
| Реальный `s3cmd`-адаптер: ключи, заголовки Content-Type и Cache-Control | интеграционный тест против MinIO: контейнер с эмуляцией S3 и настоящий `s3cmd`; публикация, затем проверка `HEAD` объектов и чтение индекса по HTTP; инъекция сбоя (недоступный endpoint, нет прав на запись) подтверждает, что индекс не меняется |
| Формат индекса и manifest для потребителя | JSON-схема индекса и фикстуры (положительные и отрицательные) в репозитории, по образцу `preview-contract`; те же файлы использует клиент DSB |
| Опубликованный плагин открывается из хранилища | post-publish smoke в workflow: прочитать индекс по публичному URL, manifest, загрузить плагин в headless Chrome в iframe страницы-хоста, дождаться `ready`; проверить заголовки и CORS |
| Очистка | режим `dry-run` печатает список к удалению; тест: билд из индекса не удаляется независимо от возраста |
| Workflows: фильтр путей, вызов из `publish-release`, `concurrency`, гейт «тест упал — записи нет» | пробный прогон `workflow_dispatch` на ветке против тестового префикса; один прогон с намеренно упавшим тестом подтверждает гейт |

### Тестовая среда: MinIO и s3cmd

Эмуляция S3 — MinIO (в DSB уже есть в локальном контуре `backend-kt/docker-compose.local.yml`, образ из `docker/minio`, path-style, бакеты создаёт `mc`). Публикация и тесты используют тот же `s3cmd`, что и CI. Особенности, которые нужно учесть:

- `S3BaseTask` вызывает `s3cmd` с `--signature-v2` и без `--no-ssl`: для локального `http://localhost:9000` задаче нужна необязательная настройка схемы (`s3-ssl=false` → `--no-ssl`); проверить, что используемая версия MinIO принимает подпись v2, при необходимости сделать вид подписи настраиваемым без изменения значений по умолчанию.
- MinIO не покрывает настоящий endpoint DSB, CORS бакета и права ключа, поэтому один проход против тестового префикса настоящего бакета остаётся в плане.
- В CI MinIO запускается шагом `docker run` (service-контейнер GitHub Actions не позволяет передать команду), бакет создаётся `mc`.

Для сквозной проверки вместе с DSB та же эмуляция служит хранилищем плагина: публикация из `plasma-android` в MinIO локального контура DSB, клиент с `VITE_COMPOSE_PREVIEW_PLUGIN_BASE_URL`, указывающим на MinIO, показывает выбранный билд.

## Risks / Trade-offs

- [Общий origin клиента и плагина: плагин в `allow-same-origin` iframe мог бы читать токены клиента] → риск принят, пока плагин публикует только команда SDDS; базовый URL — параметр; README фиксирует принятый риск; разделение origin — будущее изменение.
- [Общий бакет: выкладка клиента с `--delete-removed` удаляет файлы плагина, а публикация плагина может затронуть клиент] → раздельные не вложенные префиксы; ключ записи плагина ограничен своим префиксом.
- [Гонка при обновлении индекса] → serialised `concurrency` по каналу; после записи задача перечитывает индекс и сверяет запись.
- [Сбой между заливкой билда и обновлением индекса] → безопасно: каталог остаётся без ссылки и будет убран чисткой; индекс по-прежнему указывает на рабочий билд.
- [В `dev` версия `uikit-compose` в метке отстаёт от исходников] → клиентская проверка опирается на `apiMetaSha256`; в `dev` предупреждения о расхождении ожидаемы.
- [Новый workflow на каждый push в `develop`: сборка Wasm и браузерный тест требуют Chrome и Node] → фильтр путей; браузерный тест — гейт перед публикацией; время сборки измеряется на первой реализации.
- [`S3UploadTask` не умеет per-file заголовки] → расширение задачи в `build-system` затрагивает все included builds; регрессия проверяется на docs/dokka.
- [Публикация в публичный бакет без trust policy] → вне объёма; README плагина уже фиксирует отсутствие подписи; требует отдельного change.
- [Секреты записи в бакет DSB в этом репозитории] → отдельный ключ с правом записи только в префикс `compose-preview/`.

## Migration Plan

1. Добавить поля manifest и `api-meta.json` в артефакт (обратно совместимо: клиент игнорирует неизвестные поля).
2. Добавить задачу публикации и проверить её против MinIO, затем один раз против тестового префикса настоящего бакета (то, что эмуляция не покрывает: реальный endpoint, CORS, подпись, права ключа).
3. Включить workflow `dev`, затем `current`; `publish-release` дополняется вызовом workflow плагина.
4. Клиентский change включается после появления первых записей индекса; до этого клиент работает через `VITE_COMPOSE_PREVIEW_PLUGIN_URL`.

Откат: удалить запись из индекса канала (или вернуть предыдущий `index.json`); билды неизменяемы и не требуют отката.
