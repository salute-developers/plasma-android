## Context

База подготовки: `origin/develop`, `0b6cc75ad`. В этом репозитории ветка разработки называется `develop`.

`integration-core/preview-compose-plugin` уже извлекает `sdds/api/uikit-compose-api-meta.json` из JVM-артефакта UIKit, использует его для генерации фабрик и кладёт исходный файл в ZIP как `api-meta.json`. `generatePreviewManifest` записывает `commit`, `version = commit.take(12)`, `uikitComposeVersion` из трёх чисел в `gradle.properties` и SHA-256 меты. Существуют проверки состава ZIP и production preview в браузере. CI публикует сборки `develop` и релизных источников через DS Builder CLI.

DS Builder change `version-core-entities-and-preview` требует неизменяемые координаты `(libraryId, platform, version)`. Изменённые байты или нормализованный состав под теми же координатами отклоняются. На `develop` версия `uikit-compose` меняется реже исходников: добавления только `coreRelease` в шаблон недостаточно.

## Goals / Non-Goals

**Goals:** выпускать совместимые Compose-архивы, отделить Core от preview build ID, воспроизводимо получить A/B/B2 и передать измеримые результаты в DS Builder.

**Non-Goals:** менять генерацию кода ДС, алгоритм KSP, Kotlin API основной библиотеки, формат массива меты, Preview Protocol v1, системные состояния или серверную логику публикации. Сборка артефактов не требует публикации Maven-пакетов. Проверочное удаление не должно попасть в обычную поставку UIKit.

## Decisions

### 1. Координаты добавляются в manifest, исходная мета сохраняется

| Поле | Источник и смысл |
|---|---|
| `coreRelease.libraryId` | Постоянное `uikit-compose`, согласованное с примерами импорта DS Builder |
| `coreRelease.platform` | Постоянное `compose`, совпадает с платформой manifest |
| `coreRelease.version` | Явная версия поставляемого Core-снимка по правилам ниже |
| `uikitComposeVersion` | То же значение, что `coreRelease.version` |
| `commit` | Полный SHA исходников preview |
| верхнеуровневое `version` | Первые 12 символов `commit`; существующий build ID |
| `apiMetaSha256` | SHA-256 точных байтов `api-meta.json` из архива |

Идентификатор библиотеки не настраивается отдельно для A/B: сервер разрешает одну библиотеку на платформу. В локальном контуре с ранее импортированным другим `libraryId` нужен отдельный каталог/БД, а не автоматическое переименование библиотеки.

Существующая цепочка `previewApiMeta → extractPreviewApiMeta → generatePreviewManifest → previewPluginArtifact` остаётся. В ней один источник меты для JVM/Wasm-зависимости, фабрик, хеша и ZIP. `components` manifest по-прежнему описывает рендеримые истории; это не фильтр состава Core-меты. Не добавляем JSON-оболочку или повторную сериализацию меты.

Проверка распакованного ZIP расширяется на все координаты, их согласованность и строгий формат SHA-256. Негативные тесты намеренно повреждают копии артефакта; они не используются как успешные A/B.

### 2. Явная политика версий без изменения общих Gradle conventions

В модуле упаковки вводится параметр `previewCoreVersion`. Его эффективное значение входит в Gradle inputs и записывается одновременно в `uikitComposeVersion` и `coreRelease.version`.

- Dev CI передаёт `<baseVersion>-dev.<fullSourceCommit>`, где baseVersion берётся из `uikit-compose/gradle.properties`, а SHA — из реально выбранного checkout. Два коммита с изменившейся метой не претендуют на одну стабильную версию. При обычной локальной упаковке без параметра применяется это же правило.
- Для стабильной поставки CI передаёт `baseVersion` только после проверки источника релиза UIKit и соответствия версии. Произвольная ветка не объявляется стабильным Core только потому, что выбрано окружение `prom`; при недоказанном источнике отправка останавливается.
- A/B используют отдельные prerelease-версии `<baseVersion>-ab.a.<commitA>` и `<baseVersion>-ab.b.<commitB>`. Они поставляются только в изолированный проверочный контур.
- Для нового preview того же Core допускается явный повтор версии, если точные байты меты совпадают с исходной поставкой. B2 использует версию B и другой preview-коммит. Сервер остаётся окончательной проверкой неизменяемости; конфликт не обходится автоматической сменой версии и повторной отправкой.

Это версии Core-снимков, объявляемые производителем; Maven-координаты и версия локальной зависимости не переписываются. Для стабильного Core значение совпадает с версией UIKit, а для dev/проверки содержит явно документированный prerelease-суффикс. Клиент не выводит координаты из меты или её хеша.

Проверка артефактов для публикации требует чистые исходники и настоящий source commit. Существующий `previewCommit` разрешён только при доказанном соответствии checkout/экспортированным исходникам; произвольный SHA не является происхождением. Смена только `previewCoreVersion` также требует нового preview build ID, если предыдущий архив уже опубликован: сервер не допускает разные ZIP под одним ID. Повторная отправка использует сохранённый ZIP; воспроизводимость пересборки проверяется отдельно.

Альтернатива «версия только из gradle.properties» отвергнута из-за конфликтов на develop. Изменение общерепозиторного Maven-versioning избыточно: задача касается поставки каталога/preview.

### 3. Проверочные исходники A/B изолированы от продукта

Рецепт и исходные patch-файлы находятся рядом с модулем preview, например в `src/coreReleaseTest/`. Достаточно небольшого сценария подготовки и существующих Gradle-задач; отдельный release framework и новый included build не нужны.

Рецепт получает зафиксированный producer commit с реализацией этого change и создаёт отдельные временные checkout. Для A/B/B2 сохраняются настоящие локальные fixture-коммиты и переносимое свидетельство их исходников (Git bundle либо экспорт исходников с patch-файлами и проверяемым tree SHA). Они не пушатся в продуктовые ветки; исходный checkout не изменяется. A/B получают отдельные build directories, чтобы исключить смешение результатов KSP/Wasm.

Конкретный сценарий на текущем Core:

- **A:** исходная мета содержит `TextField.cursorColorReadOnly` и `TextArea.cursorColorReadOnly` с `deprecated.message = "Use cursorColor"`.
- **B:** в изолированной копии `TextFieldStyleBuilder.kt` удаляется только `@ApiDeprecated("Use cursorColor")` у соответствующей перегрузки. Обе перегрузки уже имеют `@Deprecated`; текущий KSP исключает их из меты без `@ApiDeprecated`. Методы остаются в Kotlin API. Мета заново получается обычным KSP, фабрики и настоящий Wasm пересобираются из B.
- **B2:** исходники Core и мета B неизменны; отдельный preview-коммит меняет только проверочную подпись плагина. Версия Core явно остаётся B, build ID отличается. B2 нужен для проверки, что поздно закреплённый preview не заменяется следующей сборкой того же Core.

Проверка рецепта требует наличия всех ожидаемых перегрузок/аннотаций и останавливается при изменившейся базе. Сравнение A/B подтверждает отсутствие ровно выбранного свойства у обоих компонентов, неизменность остальных записей и наличие совместимого `cursorColor`. Ручное редактирование `api-meta.json`, копирование Wasm из A в B и подмена manifest готового ZIP не допускаются. Структурное сравнение разрешено только для диагностики, не для записи файла меты.

Deprecated-свойство уже пропускается preview-генератором. Поэтому проверка A не требует визуального эффекта от него: проверяется сохранённая конфигурация/экспорт, warning и успешная отрисовка компонента. Для переноса выбирается свободное назначение `cursorColor` в точно той же области; отдельный сценарий выполняет удаление. Это техническая проверка переноса, а не автоматическая миграция семантики readonly.

### 4. Комплект передачи и граница ответственности

В локальном каталоге результатов, исключённом из Git, сохраняются для A/B/B2:

- `preview-compose-plugin.zip`, извлечённая из него без изменения `api-meta.json` и manifest;
- receipt с `libraryId/platform/coreVersion`, source commit/tree, build ID, SHA-256 меты и всего ZIP, базовым producer commit и checksum patch/исходников;
- команды с параметрами, версии JDK/Gradle/Node/Chrome, результаты JVM/проверки архива/browser test, ссылка на исходники, отчёт diff меты A/B;
- инструкция seed-настройки ДС с выбранными компонентом/оформлением/назначением и свободным целевым свойством; идентификаторы конкретной БД получаются при импорте, не зашиваются в переносимый fixture.

Секреты и сессии не попадают в receipt. Рецепт собирает артефакты без сети к DS Builder и не публикует их автоматически. Внешний прогон использует отдельный локальный контур с совместимыми backend/CLI из DS Builder change; реальные HTTP-коды, IDs, counts и хеши фиксируются в отдельном отчёте, а не заранее объявляются успешными.

Сценарий передачи:

1. Проверить dry-run A, опубликовать preview A через CLI и создать ДС с активным TextField и сохранённым `cursorColorReadOnly`. Явно опубликовать версию ДС A с непустым журналом, сохранить модель/экспорт/preview ID.
2. Импортировать **только мету B** с координатами B. Импорт успешен; Core меняется, revision/журнал/версии ДС — нет. Историческая A неизменна; черновик имеет блокирующий конфликт, preview B ещё отсутствует, редактор доступен. Новый fetch/export и прямая публикация отклоняются.
3. Пройти сводку → «Проблемы»; проверить удаление и перенос, сохранение/откат и конфликт параллельной правки. Для двух действий использовать независимые seed-состояния. После исправления и с непустым журналом явно опубликовать ДС B **до** публикации preview B.
4. Опубликовать ZIP B: ожидающий слот опубликованной ДС B заполняется один раз. Опубликовать B2: историческая ДС B сохраняет первый build ID, а A сохраняет A. Запустить поддерживаемую сервером очистку с посторонней незакреплённой сборкой и проверить доступность закреплённых URL/байтов. Поздняя повторная отправка A не откатывает текущий Core B.
5. Проверить локальную генерацию из сохранённого снимка A при недоступном сервере и локальном Core B. Запуск генератора не требует совпадения Core; сборка/тесты полученного кода отдельно показывают реальную совместимость.

Полный набор вариаций/сочетаний/состояний и негативных исправлений берётся из задач 8.2–8.4 DS Builder. Android предоставляет реальные артефакты; серверные assertions и UI-прогон выполняются в его контуре. Один evidence-отчёт можно использовать для обоих change, без дублирования серверного тестового инструментария в Android.

### 5. CI, документация и проверка

Расширяется существующий workflow: определение явной версии Core, прежние тесты/сборка, проверка архива, совместимый закреплённый CLI, dry-run и разрешённая отправка. Версия CLI выбирается по реально опубликованному релизу с `coreRelease`, номер не выдумывается. Пока такого релиза нет, локальный прогон использует CLI из DS Builder worktree; автоматическая отправка остаётся выключенной. A/B-рецепт не вызывает prom workflow.

README обновляет таблицу полей, параметры, политику dev/release, происхождение меты и инструкцию A/B. Старое обещание «повторная отправка старого коммита откатывает Core» убирается: повтор не переключает текущий Core назад. Новые публичные Gradle-типы, если понадобятся, документируются KDoc; общий DSL `dsBuilder` и его генераторы не расширяются ради этой задачи.

Основные команды запускаются из корня репозитория, для каждого проверочного checkout и с его `-PpreviewCoreVersion`:

```bash
./gradlew -p integration-core :preview-compose-plugin:jvmTest
./gradlew -p integration-core :preview-compose-plugin:previewPluginArtifact :preview-compose-plugin:verifyPreviewPluginArtifact
./gradlew -p integration-core :preview-compose-plugin:previewPluginBrowserTest -PpreviewChromePath=<chrome>
```

Негативные тесты validator/version selection добавляются в тот же модуль с документированной командой запуска. Линтеры запускаются по затронутым модулям. Если потребуется изменить KSP или общие conventions, это выходит за выбранное узкое решение и требует пересмотра design.

## Risks / Trade-offs

- [Dev-версия отличается от Maven-версии] → явно документировать смысл `uikitComposeVersion` как версии поставляемого Core; сохранять baseVersion и source SHA в receipt, не менять Maven dependency resolution.
- [Один commit и разные параметры дают разные ZIP с одним build ID] → отдельный source commit для каждой публикуемой поставки, фиксированные параметры/receipt и отказ сервера на перезапись. Текущий формат build ID сохраняется.
- [Изменилась форма TextField API] → проверять предусловия patch и точный diff меты; не выбирать другое свойство молча.
- [Невоспроизводимый ZIP или потерянные локальные fixture-коммиты] → хранить оригинальные ZIP, хеши, переносимые исходники и проверять повторную сборку. Без источников проверка не считается воспроизводимой.
- [Старый CLI/backend либо отсутствующий browser/S3] → prerequisite отмечается отсутствующим, внешний этап не считается пройденным.

## Migration Plan

1. Реализовать и проверить producer локально; согласовать пример `uikit-compose/compose/version` с DS Builder.
2. Получить A/B/B2 и пройти связанный локальный контур. Не отправлять проверочные prerelease в общие dev/prom каталоги.
3. Перед включением CI развернуть совместимый backend и закрепить выпущенный CLI. Пересобрать архивы из исходников; старые ZIP не исправлять на месте.
4. При проблемах выключить автоматическую отправку. Уже сохранённые Core/preview не удаляются и не перезаписываются; исправление выпускается под новыми координатами/ID. Возврат старого producer без нового manifest несовместим с новым сервером.

## Open Questions

- Какой опубликованный релиз DS Builder CLI станет первым совместимым? Это условие включения CI; локальная сборка CLI позволяет выполнить A/B до его выпуска.
- Конкретные SHA producer/A/B/B2 и контрольные суммы появятся при реализации. Они не заменяются фиктивными значениями в этом proposal.
