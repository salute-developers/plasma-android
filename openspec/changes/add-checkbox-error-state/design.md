## Context

Compose `CheckBox` (`sdds-core/uikit-compose/src/commonMain/kotlin/com/sdds/compose/uikit/CheckBox.kt`) сегодня принимает состояние как `androidx.compose.ui.state.ToggleableState` — закрытый enum AndroxX (`On`/`Off`/`Indeterminate`), который нельзя расширить. Отрисовка галочки/палочки (`CheckBoxControl.kt`) построена на одном непрерывном 3-точечном пути: галочка морфится в палочку через `crossCenterGravitation`, стягивающий концы к центру. Стилевой слой (`CheckBoxStates : ValueState`, `CheckBoxColorValues`) — открытый, наш собственный, расширяется без проблем.

В кодовой базе уже есть неиспользуемый путь отрисовки через внешние Composable-иконки (`icons: CheckBoxIcons?` в `CheckBoxControl.kt`, в проде всегда `null`) — при его использовании reveal/morph-анимация полностью отключается. Это прямое доказательство, что вынесение отрисовки вовне несовместимо с требованием анимации.

Имя `Negative` для нового состояния использовать нельзя — оно уже занято `WrapperCheckBoxView.Negative` в `tokens/plasma.giga.compose` для цветового варианта (не глифа).

`CheckBoxGroup.kt` — чистый layout-контейнер, не хранит и не считает checked-состояние; вся roll-up логика (parent/children) живёт только в демо-фикстуре `CheckBoxGroupStory.kt` как образец для потребителей.

## Goals / Non-Goals

**Goals:**
- Добавить состояние **Error** (крестик) как 4-е value-состояние Compose `CheckBox`, без breaking changes для существующих вызовов.
- Сохранить анимацию появления/переключения на уровне, сопоставимом с существующими состояниями.
- Заложить лёгкое место для будущих состояний (без over-engineering).
- Обновить демо в сэндбоксе, включая пример roll-up логики в `CheckBoxGroupStory`.

**Non-Goals:**
- View-система (`sdds-core/uikit`) — не трогается.
- Генерируемые per-brand файлы стилей `tokens/*/styles/checkbox/CheckBoxStyles.kt` (giga, finai, sbcom, serv, stards, homeds и др.) — **вне скоупа, не трогаются вообще**. Они помечены `AUTO-GENERATED. DO NOT MODIFY` и производятся themebuilder-пайплайном из токен-источников в отдельном репозитории `theme-converter` (`checkbox_config.json` по вертикалям). Донастройка per-brand цветов Error (и любые изменения цветовых схем, например добавление `Positive` рядом с `Default`/`Negative` для `plasma_giga`) ведётся владельцем токенов отдельно, вне этого changes и вне этого репозитория.
- Универсальный open plugin/registry для сторонних состояний — сознательно не строим, состояний в обозримом будущем немного, кандидатов сверх Error сейчас нет.
- Изменение `CheckBoxGroup.kt` — компонент остаётся чистым layout-контейнером.

## Decisions

### 1. Публичный API — новый параллельный enum + новые перегрузки
`ToggleableState` не трогаем (закрытый тип AndroidX). Вводим новый публичный enum (4 значения: Off/On/Indeterminate/Error) и добавляем новые composable-перегрузки `CheckBox(...)`, принимающие его, рядом с существующими. Старые перегрузки продолжают работать как раньше — расширение чисто аддитивное.

*Альтернатива*: булев флаг `error: Boolean` поверх `state: ToggleableState`. Отклонено — противоречит решению "Error — состояние значения, а не оверлей", создаёт семантически неоднозначные комбинации (`state=Checked, error=true`).

### 2. Отрисовка — свой parametric-path, не внешние иконки
Крестик рисуется тем же механизмом, что и галочка/палочка в `CheckBoxControl.kt` (Path + PathMeasure reveal), а не через Composable-иконки.

*Обоснование*: единственный путь через внешние иконки уже существует в коде (`icons: CheckBoxIcons?`) и **не имеет анимации** — при его использовании `checkDrawFraction`/`crossCenterGravitation` не участвуют вообще. Дополнительные минусы внешних иконок: лишняя composition/layout нагрузка на элемент в списках/группах, потеря точного пропорционального масштабирования геометрии между брендами, риск инвалидации golden-скриншотов в ~8 `*CheckBoxScreenshotTest.kt`.

### 3. Геометрия крестика
Две независимые диагонали внутри той же рамки `0.3…0.71` по обеим осям, что использует текущая галочка (`leftX`/`rightX` в `drawCheck`), тот же stroke width и `StrokeCap.Round` — для одинакового визуального веса всех глифов независимо от бренда/размера контрола.

*Открытый момент*: точные цифры стоит сверить с Figma-спекой, если она есть — референс с скриншота (иконка-приложение) использовался только как референс формы, не как pixel-exact источник.

### 4. Тайминг анимации — "семьи" глифов
- Переход **через Off** (появление/исчезание) → существующий `tween(animationDuration)`, без изменений.
- Прямой переход между непустыми состояниями **внутри одной семьи** (`On ↔ Indeterminate`, общий путь) → как сейчас, `spring()`-морф через `crossCenterGravitation`.
- Прямой переход между **разными семьями** (`On`/`Indeterminate` ↔ `Error`) → **кроссфейд** (альфа старого глифа к 0, альфа нового к 1), а не морф общего пути — крестик геометрически не совместим с 3-точечной моделью галочки/палочки.

Это вводит понятие **"семьи" глифов**: `{On, Indeterminate}` — одна семья (общий путь, морф), `Error` — отдельная семья (кроссфейд по умолчанию). Явное правило на будущее: новое состояние по умолчанию становится отдельной семьёй (дёшево, безопасно); совместный морф с существующей семьёй — осознанное дорогое решение, только когда оправдано дизайном.

### 5. Внутренняя консолидация состояний (лёгкая, без registry)
Сегодня переключение по `ToggleableState` разбросано по 4 независимым `when`-блокам (`BaseCheckBox.SideEffect`, `checkDrawFraction`, `checkCenterGravitationShiftFraction`, `IconsContent`). Сводим их в **одну** внутреннюю таблицу состояние → { семья, геометрия, reveal-стиль }, к которой оба публичных API (старый `ToggleableState`-based и новый) маппятся перед рендером. Это разовый рефакторинг ради Error, не полноценный plugin-фреймворк — открытого механизма регистрации состояний снаружи библиотеки не строим.

### 6. Error — только программно, никогда через клик
`CheckBox` — управляемый (controlled) компонент: `state` приходит от вызывающего кода, клик лишь вызывает `onClick`/`onCheckedChange`. Сам компонент никогда не переводит себя в Error — это уже гарантируется архитектурой, менять в библиотеке нечего. Меняется только demo-логика click-цикла в фикстурах (см. ниже).

### 7. Стили — расширение существующего паттерна, только ядро
`CheckBoxStates.Error` добавляется как новое значение `ValueState` (маркер-интерфейс, открытый). Цвета (`toggleColor`, `toggleBorderColor`, `toggleIconColor`, `backgroundColor`) заводятся через существующий `StatefulValue<Brush>` в `CheckBoxColorValues`, по аналогии с уже существующими ключами `CheckBoxStates.Checked`/`CheckBoxStates.Indeterminate`. Генерируемые per-brand стили не трогаем (см. Non-Goals) — раскатка цветов по вертикалям происходит отдельно через `theme-converter`.

Fallback-плейсхолдер в `DefaultCheckBoxColorValues` (`sdds-core/uikit-compose`) — библиотечный дефолт, а не продуктовый цвет: сегодняшние Checked/Indeterminate там уже захардкожены как `Color.Green` (см. `CheckBoxStyle.kt`), реальные приложения его не видят, так как всегда используют бренд-стиль из `tokens/*`. По аналогии для Error используется `Color.Red` — такая же условная заглушка, а не дизайн-решение.

### 8. Сэндбокс — `CheckBoxStory`
Свойство `CheckBoxUiState.state` меняет тип с `ToggleableState` на новый enum. Пикер в панели свойств сэндбокса генерируется KSP через generic `enumProperty<reified E : Enum<E>>` (`integration-core/sandbox-core/.../Properties.kt`), которая работает с любым Kotlin-enum через `enumValues<E>()` — переписывать UI-код пикера не нужно, он пересоберётся сам по типу поля. Меняется только локальный click-хелпер: `Off/Indeterminate/Error → On`, `On → Off` (Error никогда не производится кликом, только внешним присвоением).

### 9. Сэндбокс — `CheckBoxGroupStory` (roll-up)
`CheckBoxGroup.kt` не меняется. Демо-функция `getParentState()` в `CheckBoxGroupStory.kt` дополняется приоритетной веткой Error — если хотя бы один child в Error, root тоже становится Error, проверяется первым:
```kotlin
when {
    any { it.state == Error } -> Error
    all { it.state == On } -> On
    all { it.state == Off } -> Off
    else -> Indeterminate
}
```
Клик по child/root использует тот же обновлённый хелпер, что и в п.8 — клик по Error-child выводит его в On, после чего root пересчитывается обычным образом.

## Risks / Trade-offs

- **[Риск] Появление нового публичного enum рядом с `ToggleableState` увеличивает когнитивную нагрузку на потребителей API (два способа задать состояние).** → Смягчение: чёткая KDoc с указанием, что новый enum — единственный путь получить Error, старые перегрузки помечаются как достаточные только для 3-состояний.
- **[Риск] `@ApiStateSet(components = ["CheckBox"])` участвует в api-info/themebuilder кодогенерации — не до конца ясен эффект от нового значения на генератор.** → Смягчение: после реализации прогнать генератор и сверить вывод по существующему процессу (см. `themebuilder-generated-output-workflow`), зафиксировать как проверочный шаг в tasks.md.
- **[Риск] Кроссфейд между семьями (в отличие от морфа) может визуально ощущаться "менее плавным" на быстрых сериях кликов/групповых операций.** → Смягчение: это осознанный компромисс (см. Decision 4), совместный морф Error с check/dash не запрашивался и не оправдан геометрически.
- **[Риск] Screenshot-тесты в brand-модулях (`*CheckBoxScreenshotTest.kt`) не покрывают новое состояние — генерируемые стили этих модулей вне скоупа, у Error там пока нет собственного цвета.** → Смягчение: golden-тест на Error заводится только в `sdds-core/uikit-compose` (на fallback-цвете); per-brand покрытие появится само после того, как `theme-converter`/themebuilder перегенерируют стили с цветами Error.
- **[Trade-off] Крестик в brand-темах будет выглядеть на fallback-цвете ядра, пока владелец токенов не донастроит `checkbox_config.json` per-brand.** → Осознанно принято: генерируемые файлы не трогаем в этом изменении (см. Non-Goals), это отдельный процесс в `theme-converter`.
